**チーム**：運用・データ・デバッグ（`.claude/agents/ops.md`）。ラベル「運用」（色 BFD0B0）。枝の頭 `ops`。

**定例（毎回。issue の前にする）**：毎晩の巡回は GitHub Actions「巡回」（`.github/workflows/patrol.yml`。04:00 UTC に本番を読むだけの検査 `scripts/check/expect.py`）。このクラウドからは本番に届かないので、結果は GitHub で読む。
1. `gh run list --workflow 巡回 --limit 3 --json databaseId,conclusion,createdAt,url` で直近の結果を見る。
2. 失敗の issue（題の頭「巡回 」、開いているもの）を見る：`gh api -X GET $R/issues -f state=open -f per_page=50 --jq '.[] | select(.pull_request|not) | select(.title|startswith("巡回 ")) | [.number, .title] | @tsv'`。あれば本文の × と △ の行を読む（記録は `gh run download <id> -n 巡回の記録 -D /tmp/junkai` で取れる。合言葉は入っていない）。
   - コードの不具合らしければ、再現の手順（どの口座の役・どの口・何が返った）を issue にコメントし、ラベル「コード」を足す。
   - 本番の反映や設定が要る（本人の手）なら、issue に命令文をコメントしてラベル「本人」を足す。
   - 一時のもの（通信の失敗など）なら、翌晩の結果を待つとコメントし、2 晩続いたら上の 2 つのどちらかにする。
3. 月曜なら、`knowledge/10-現状.md` の「本番を読むだけの検査」の行を直近の巡回の数（件数・△・口座の数・日付。`gh run download` した expect.log の最後の行）に直し、枝 `ops/現状-YYYY-MM-DD` で PR を出す（数が減っていたら理由を書く。理由が言えなければ「減った」とだけ書いて、直さない）。 同じ日に issue「巡回 YYYY-MM-DD（週の控え）：PR を作れなかった」が開いていれば、その本文の JSON を `scripts/check/ledger-production.json` に写して同じ PR に入れ、issue に PR の link をコメントする（Actions の token が PR を作れない設定のあいだの道。Artifacts はこのクラウドから取れない ―― 403）。
4. 本番の反映（`sh deploy/更新.sh` など）は本人だけ。チームは命令文を用意するまで。

**作法の要点**：巡回は 1 回 10 万トークン以内。減った数は理由を言えるまで写さない。見つけた不具合は「どの画面・何をしたら・どうなった・再現手順」で issue。
