# 進捗を「生徒ごとに分けて持つ」ための設計

作成日: 2026-07-31
対象: `app/` のプロトタイプと、その先の本番構成

前提は `HANDOVER.md`。本書はそのうち **3.2 保存層** を実装まで落としたもの。

---

## 0. 結論だけ先に

**分けるのは進捗だけ。教材は分けない。**

進捗は1人あたり**実測で95KB**（全1,590項目を解き切った場合）。
生徒50人で **4.6MB**。つまり「全校分」がスマホの写真1枚に収まる。

この大きさなら、
段階を踏まずに設計を作り込む必要はない。**同じデータの形のまま、
置き場所だけを3段階で移していける。** それが本書の主旨。

| 段階 | 置き場所 | 講師が見られるか | 必要なもの |
|---|---|---|---|
| **L0** | 生徒の端末の中 | 見られない | なし（**動いている**） |
| **L1** | 端末＋書き出し／提出コード | 手渡しで見られる | なし（**動いている**） |
| **L2** | サーバ | いつでも見られる | サーバ1台とドメイン（**仮サーバで動いている**） |

アプリは起動時にサーバの有無を自分で確かめ、入口だけを切り替える
（サーバあり＝ID/パスワード、なし＝クラスコード）。学習の画面は同じ。
サーバを止めても生徒の手元は壊れない。

試用のための仮サーバは `server/tube_server.py`（このMacの中だけ・TLSなし）。
使い方は `README.md`。ここから先が「本番のサーバをどこに置くか」の話。

---

## 1. 原則 ―― 共通のものと個人のものを混ぜない

教材（単語・語法・文法）は、**誰の端末でも同じで、書き換わらない**。
だから保存の対象ではない。アプリと一緒に配ればいい。

保存するのは、その子が**いつ・何を・どれくらい覚えたか**だけ。
これは1項目あたり数十バイトしかない。

```
教材   packs/core.js   369KB   全員共通・読み取り専用・更新はアプリの更新と同時
進捗   1人ずつ別の鍵     ~95KB   その子だけのもの・毎問更新される
```

この線を引かないと、生徒ごとに教材のコピーを持つことになり、
教材を1語直すたびに全員分を書き換える羽目になる。

---

## 2. 鍵の切り方（実装済み）

```
tube.school.v1.roster        この端末にいる生徒の一覧（名前・学年・クラス）
tube.school.v1.p.<sid>       生徒1人分の進捗。1人1鍵
tube.school.v1.device        端末のID
```

`<sid>` は8文字の記号（`K7M2QRPT` など）。**氏名は入らない。**
サーバがいればサーバが発行し、いなければ端末が発行する。
端末側で振り直さないのが肝心で、そうしないと同じ生徒が端末ごとに別人になる。

鍵を分けてあることで、そのまま次が成立する:

- **教室の共用iPadに複数人が同居できる**（実際に必要になる）
- 1人分だけ**書き出す／消す／送る**が自然にできる
- ある生徒のデータが壊れても**他の生徒に波及しない**
- サーバに移すとき、鍵がそのままURLになる（`/p/<sid>`）

### 進捗そのものの形

```jsonc
{
  "v": 1,
  "sid": "K7M2QRPT",
  "level": "j2",
  "cards": {
    // [間隔日数, 易しさ係数, 次回出題, 回数, 忘れた回数, 最終, 既知フラグ]
    "v:reluctant:adj": [21, 2.5, 1785000000000, 4, 0, 1783200000000, 0]
  },
  "hist": { "2026-07-31": {"n": 42, "ok": 38, "done": 1} },
  "streak": 12, "best": 19, "xp": 840,
  "savedAt": 1785000000000, "rev": 137
}
```

`cards` を配列に詰めているのは、鍵名が1,590回繰り返されるのを避けるため
（オブジェクトのままだと倍近くなる）。**実測61バイト／項目。**

`items.id` は必ず内容由来（`v:reluctant:adj`）。配列位置を使うと、
教材の途中に1語挿しただけで全生徒の進捗がズレる（HANDOVER 5.2）。
**学年を変えても記録が消えないのはこの設計のおかげ。** 進捗は項目に
紐づいていて、学年やクラスには紐づいていない。

## 3. L0 ―― 端末の中（いま動いている）

3系統に同時に書き、起動時にいちばん新しいものから復元する。

```
localStorage     ふつうの保存先
sessionStorage   同じタブのリロードなら、localStorage が消えても拾える
IndexedDB        容量が大きく、Safari の掃除にも比較的強い
```

生き残った1つから復元したあと、**そのコピーを全系統に書き戻す**。
1つでも生きていれば他が自動で修復される。

### 落ちないために守っていること

`HANDOVER.md` 5.1 の再発防止。すべて `tools/check.js` が機械的に検査する。

| 守ること | なぜ |
|---|---|
| 書けるかは**実測**する（書いて読み返す） | `try/catch` だと「遮断」と「まだ空」が区別できず、警告が一度も出ないまま消え続ける |
| 読み取りが空のときは**書き込まない** | 空を本物の上に書いて全滅させた実例がある |
| 「遅い」を「空」と誤判定しない | 携帯の IndexedDB は初回オープンが遅い。再試行してから結論を出す |
| 診断の持ち主は `boot()` ひとつ | `save()` が結論を上書きすると `blocked` の判定が潰れる |
| 遅延書き込みのタイマーは**鍵ごと** | 使い回すと名簿の保存が進捗の書き込みを取り消す |

失敗したときは**画面のいちばん上に出す**。黙って落とさない。

### L0 の限界（正直に）

- 端末を変えたら消える → L1 の書き出しで運ぶ
- 講師が見られない → L1 の提出コード、または L2
- **ブラウザの「履歴を消去」で消える** → これは L2 でしか根本解決しない

## 4. L1 ―― サーバなしで講師に届ける（いま動いている）

サーバを立てる前に運用を始められるように、経路を2つ用意した。

**① 書き出しファイル**（設定 → 記録を書き出す）
1人分または端末の全員分を `.json` で保存する。端末の乗り換え・バックアップ・
講師への提出に使える。取り込み時は `savedAt` が新しい方を残す。

**② 提出コード**（記録画面の下に出る）

```
K7M2QRPT-C-1F-2A-9-3B
   sid   14日 のべ 定着 連続 検査
```

生徒が見せ、講師が「管理 → 提出コードを読む」に打ち込む。20文字程度。
**打ち間違いは弾けるが、改竄は防げない。** 出欠の代わりであって成績ではない。
厳密さが要るなら L2 へ。

## 5. L2 ―― サーバ同期（仮サーバで実装・実測済み）

`curriculum.js` の同期先を書き換えるだけで預け先を移せる。

```js
sync: { base: '/api' }                          // 同じ場所から配信（いまの形）
sync: { base: 'https://tube.example.org/api' }  // 別のサーバに預ける
sync: null                                      // 探しにいかず端末内だけで動く
```

### 実測できたこと（2026-07-31・仮サーバ）

- 2つのアカウントで学習 → サーバ上に**生徒ごとの別ファイル**として保存される
- 端末の記録を**すべて消して**ログインし直すと、サーバから進捗が戻る
- 生徒は他人の記録を**読めない・書けない**（403）
- 講師は担当クラスを**読めるが書けない**（403）
- 古い記録を送ると **409** で弾かれ、新しいほうが残る
- 講師の名簿は、その端末で学習したことのない生徒も含めて全員が見える

### サーバに求める仕様（これだけ）

```
GET  /api/health      -> {ok:true}                  サーバの有無の見分け
POST /api/login       <- {id, password} -> {token, profile}
POST /api/logout
GET  /api/me          -> {profile}
GET  /api/p/{sid}     -> 200 {rev, savedAt, blob} / 404
PUT  /api/p/{sid}     <- {rev, savedAt, blob}   409 なら相手が新しい
GET  /api/class       -> {students:[{profile, savedAt, blob}]}   講師用
```

- 認証は `Authorization: Bearer <token>`
- **「生徒は自分の sid だけ、講師は担当クラスだけ」の判定はサーバ側で行う。**
  クライアントの判定は判定ではない
- オフライン中の保存は送信待ちに溜まり、オンライン復帰で送られる
  （通学の電車内で解いて、駅を出たときに同期される想定）
- 衝突は `savedAt` が新しい方を採用。同じ生徒の複数端末しか想定していないので足りる

### どこに置くか

| | 向いている点 | 引っかかる点 |
|---|---|---|
| **Supabase**（推奨） | Postgres + 行レベル権限。「生徒は自分の行だけ」をDBで担保できる。無料枠で50人は余裕 | 事業者が米国企業。**データの所在地をEU/UKに指定すること** |
| **校舎のサーバ** | データが校舎から出ない。説明が最も簡単 | 誰が保守するかを先に決める。バックアップと証明書の更新が要る |
| **Cloudflare Workers + KV** | 鍵と値を預かるだけなので実装が数十行。安い | 講師用の集計は自前で書く |

進捗は**鍵と値だけ**なので、どれでも実装量は変わらない。
選ぶ基準は技術ではなく、**誰が保守するか**と**データをどこに置くか**。

### 未成年のデータであること（着手前に決める）

中1〜中3は**12〜15歳**。UK GDPR では 13歳未満の同意は保護者に依る。
実装で先回りできることは全部してある:

- サーバに送るのは **sid と進捗だけ**。氏名は端末の名簿にしか無い
- メールアドレス・パスワード・生年月日を**一切集めない**
- 自由記述欄が無い（生徒が個人情報を書き込む場所がない）

残るのは運用の決めごと。**L2に進む前に校舎と確定させること。**

1. 保護者への説明と同意の取り方
2. データの保存期間と、卒業時の消去手順
3. データの所在地（EU/UK に置く）
4. 生徒名と sid の対応表を誰が持つか（＝端末の名簿。これが実質的な個人情報）

## 5.5 宿題 ―― 個別に出して、期限内に解かせる

サーバが持つのは**指示だけ**。単語そのものは持たない（市販教材の
語の選定・訳語は編集著作物のため。HANDOVER 4章）。

```jsonc
// server/data/assignments.json
{
  "id": "ae9ddfa9d",
  "title": "GRIT No.1000-1050",
  "source": "grit2500",        // curriculum.js の sources
  "from": 1000, "to": 1050,
  "classId": "j2a",            // クラス一括のとき
  "students": [],              // 個別に出すときは sid を並べる（こちらが優先）
  "dueAt": 1786…, "assignedAt": 1785…,
  "note": "小テストは金曜"
}
```

達成状況は**生徒の進捗ブロブの中**（`p.hw`）に入れてある。宿題のためだけに
別の保存経路を作ると、そこだけ消える ―― 既にある同期にそのまま乗せる。

```jsonc
"hw": { "ae9ddfa9d": { "done": {"1000":1, "1003":1}, "completedAt": null } }
```

番号は SRS にも載る（項目ID `grit2500:1024`）。一度「覚えた」と答えた番号も
間隔をあけて戻ってくるので、宿題が一度きりで終わらない。ただし戻る先は
宿題の中だけで、ふだんの学習には混ざらない ―― 混ぜると「今日の宿題は
終わったのか」が生徒にも講師にも分からなくなる。

**誰に出ているかの判定はサーバが行う。** 生徒には自分宛のものだけが返り、
作成・更新・削除は講師だけができる（実測: 対象外の生徒には0件、
生徒からの POST / DELETE は 403）。

## 6. 認証（生徒にメールを持たせない）

**サーバがあるとき（L2）** ―― IDとパスワード。どちらも講師が発行して手渡す。

```
講師 → python3 tube_server.py add j2a04 "佐藤 花子" --class j2a --level j2
生徒 → 渡されたIDとパスワードで入る。合言葉は30日もつ
端末変更 → 同じIDで入り直すだけ。進捗はサーバから戻る
忘れた → 講師が passwd で付け替える（古い合言葉はその場で無効になる）
```

パスワードは pbkdf2-sha256 を20万回まわしたハッシュだけを保管し、平文では持たない。
存在しないIDでも同じ返事と同じ待ち時間を返す（「そのIDはある」と教えない）。
**生徒にメールアドレスを持たせない方針は変えていない。**

**サーバがないとき（L0/L1）** ―― クラスコードと名前だけ。

```
生徒 → コード＋自分の名前で参加。以後この端末では選ぶだけ
端末変更 → コードを入れ直し、書き出しファイルを取り込む
```

この形の講師コード（`LDN-STAFF`）は**簡易な仕切りであって認証ではない**。
`curriculum.js` に平文で書いてある以上、生徒が読もうと思えば読める。
サーバ運用に移るまでは、講師用の端末を分けること。

## 7. 進める順序

| | やること | 終わったと言える条件 |
|---|---|---|
| **済** | L0/L1/L2 の仕組み | 検査が全項目通る。別端末から進捗が戻る |
| **いま** | 仮サーバで1クラス試用 | 生徒が2週間続ける。記録が1件も消えない |
| 次 | 教材を受験用に差し替え | `curriculum.js` だけの変更で切り替わる |
| その次 | 常時動くサーバへ移す | Macを閉じても動く。TLSがある。保護者への説明が済んでいる |

**常設サーバの前に、まず2週間の試用を通すこと。**
インフラを先に作ると、「毎日開かれるか」という本当の問いへの答えが
運用の作業に埋もれる。成功の定義は機能の数ではない（HANDOVER 1.4）。

移すときに書き換えるのは `curriculum.js` の1行だけで、
`server/data/` をそのまま持っていけば記録も引き継げる。
