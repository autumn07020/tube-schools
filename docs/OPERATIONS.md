# Tube for Schools — 運用設計（最終案・2026-08-11）

早稲田アカデミー ロンドン校／生徒約50名（中心は小学生6〜12歳、中学生が混在）／設定するのは英語講師1人、IT担当はいない

## 0. 前版から変えたところ（3つのレンズを受けて）

前の案には、**そのまま配ると子どもが締め出され、氏名が漏れ、運用が半年で止まる**穴がありました。骨格（EU圏VPS／NASはバックアップ専用／氏名対応表をサーバに載せない／サーバ側マージ）は正しかったので残し、以下を差し替えています。

| 前の案 | 最終案 | 変えた理由 |
|---|---|---|
| 使い切りの登録コード | **再利用できる入室カード（紙1枚・何度でも使える）** | 使い切りだと、保護者PCのSafariが7日でデータを消した瞬間に家庭が自力復旧できない。週1リズムの宿題はその境界の真上にいる |
| 共用PCは4桁PIN・失敗5回で登録破棄 | **PINを作らない。座席番号のタイルを選ぶだけ** | 小1が5回打ち間違えて締め出される代償が、守れるもの（兄が弟の記録を開く）に見合わない。そもそも第2要素として成立していない |
| 講師にTOTP（二要素） | **当面入れない。**講師アカウントを2つ＋長いパスフレーズ＋クラス限定の実装 | 復旧経路がないまま入れると、機種変1回で登録カードを出せる人がゼロになる |
| 4タブ | **3タブのまま。**「きょう」のカードを6→3に減らす | 小1に「きょう」と「しゅくだい」の区別はつかない。情報を減らす目的は、置き場所を増やさずに達成できる |
| 毎晩NASへ rsync ＋ restic 2系統 | **VPSが暗号化した1ファイルを吐き、NASはそれを引くだけ**＋Hetznerの自動バックアップ | 前案は「NASは危険」と書いた直後に、そのNASへ全データの平文複製を毎晩送っていた。部品も3つあり全部静かに壊れる |
| ストリーク→「今月やった日 18/31」 | **分母を出さない。「今月 12日」だけ** | /31 は「31日やるのが正解」と読める。休みがちな子には失敗率の常時表示になる |
| ことばの地図・校舎全体の語数・先生の「みました」印を同時導入 | **初年度は入れない。**モチベ施策は2つに絞る | 3つとも人の継続的な行動が前提。運用が要る施策を初年度に3つ足すと全部止まる |
| Phase 0 の1番目 = `peer_ip()` 修正 | **Phase 0 の1番目 = ソースをバージョン管理下に置く** | ソースは依頼者のiCloud 1箇所にしかなく、バックアップ設計は `data/` しか引かない。VPSが飛ぶとデータは戻るがアプリが戻らない |
| （記述なし） | **入口B（無認証＋氏名入力）の削除** | `app/js/ui.js:271-330` に、サーバに繋がらないと出る「はじめての人はここに名前」（placeholder「山田 太郎」）が実装済みで動く。**「氏名を一切保存しない」は、いまのコードでは事実ではない** |

## 1. 結論 ── 4つの要求と2つの問いへの答え

### 依頼者の4つの要求

| # | 要求 | 答え |
|---|---|---|
| 1 | 生徒のスマホ／保護者のPCで広く使える | **ドイツの小さなVPS 1台に置き、独自ドメイン＋HTTPSで配る。**校舎の機材に依存させない。入室は紙のカード1枚（家庭が保管し、何度でも使える） |
| 2 | どの端末で勉強しても直後に他の端末で同期 | **現状ゼロ点。最優先で直す。**いまはログイン時にしか取りに行かず、しかもオフラインで解いた分を無言で捨てる経路が実在する（`app/js/sync.js` の409分岐） |
| 3 | 宿題／毎日やること／提出履歴／モチベが1つにまとまったUI | **3タブに収める（増やさない）。**下に対応表 |

要求3の4項目と3タブの対応：

| 要求された項目 | 置き場所 |
|---|---|

### 問い1：パスワードは必要か？

**必要です。ただし、子どもが覚えるパスワードは要りません。紙のカード1枚に置き換えます。**

理由は2つ。

**① IDだけにはできない。** IDは `j2a01` `j2a02` … と機械的に並んでいるので、1つ知れば全部推測できます。教室の中では `中2A-01` は仮名ではなく「ケンタくん」で、氏名を持たない設計は同級生・兄弟に対して何の防御にもなりません。UK GDPR Art 32 に明白に反します。

**② いまの `word-1234`（40万通り）も弱い。** 50アカウント横断で試されると1日約38,400試行、期待値で約10日に1口が破れます。コードのコメント自身が「強さを担う実体は試行制限のほう」と認めています。子どもに負担を課している割に、その負担が強度に変換されていない状態です。

**答え：秘密は残す（強くする）。ただし記憶させない。**

| 項目 | いま | これから |
|---|---|---|
| 生徒が覚えるもの | ID と `word-1234` | **なし** |
| 家庭が持つもの | なし | **入室カード（紙1枚）**。引き出しに入れておく／写真を撮っておく |
| 秘密の強さ | 40万通り（19ビット） | **約10億の10億倍（60ビット）**、ソルト付き scrypt で保存 |
| 入力の回数 | 2週間に1回、50人で月100回 | **端末ごとに1回だけ**。以後ログイン操作なし |
| Safariがデータを消した／PCを買い替えた | 講師にパスワード再発行を頼む | **カードをもう一度入れるだけ。**講師に会わなくてよい |
| カードを無くした | — | 講師が再発行（旧コードは即無効＋その生徒の全端末を同時に切る、1操作） |

**カードの中身は3つだけ。氏名は書きません。**

```
   ┌─────────────────────────────────┐
   │  つうしん                       │
   │  https://xxxxxx.org              │
   │                                  │
   │  ちゅう2 A ― 07                  │
   │                                  │
   │  J2A07-K7M4-Q9XT-2P46            │
   │                                  │
   │  ※ おうちのかたが保管してください   │
   │    なくしたら先生にもう1枚もらえます  │
   └─────────────────────────────────┘
```

1行を1回貼るだけ。先頭がID、後ろが秘密。紛らわしい I・L・O・U・0・1 を除いた32文字種×12桁。

**なぜ「使い切り」をやめたか。** 使い切りコードは「先に使われた子が『入れません』と来る＝盗難の検知手段になる」という利点がありました。しかし、(a) 講師には「盗まれた」と「Safariに消された」が区別できないので、実際には何も疑わず再発行される、(b) macOS Safari は7日間そのサイトに触らないとスクリプトが書いたストレージを消すので、**週1リズムの宿題では締め出しが常態化する**。検知の価値より、家庭が自力で戻れる価値のほうが圧倒的に高い。盗難対策は別の手段（下の端末一覧）で取ります。

**端末の管理（前案に無かった部分）**

| 項目 | 決定 |
|---|---|
| 端末トークンの寿命 | 使っていれば切れない（180日ローリング）。**3月末の一括失効はやらない**（新年度の初回授業が全員ログイン不能で始まる崖を作らない） |
| 1生徒あたりの生存トークン | **上限4本。**5本目を登録すると最も古いものが自動で切れる |
| 講師画面 | その生徒の端末一覧（最終利用日だけ。機種名は取らない）と、1本ずつ／全部を切るボタン |
| 棚卸し | 年度初めに週報の1行として「180日以上使われていない端末 N本」を出す。押すだけで一括失効 |

**PINは作りません。** 共用の保護者PCでは、開いたときに座席番号のタイルが並び、押して入るだけ。「兄が弟の記録を見られる」は**受け入れる残余リスク**として保護者向け通知とDPIAに明記します（前案のPINも、暗号文が同じlocalStorageにある以上オフラインで1万通り試せるので、そもそも壁になっていませんでした）。

**講師側**

| 項目 | 決定 |
|---|---|
| ログイン | ID＋パスフレーズ（`kaede-mori-hikari-4821` 形式、800億通り以上）。トークン12時間は据え置き |
| 二要素（TOTP） | **入れない。**入れるなら「講師アカウント2つ＋印刷したリカバリコード＋監査付きCLIリセット」が同時に揃ってから（Phase 3以降） |
| 先に効く対策 | ①生徒のパスワードログイン廃止（スプレー攻撃の的が消える）②講師の一括取得を廃止（漏れたときの被害が実際に小さくなる）③**クラス限定を本当に実装する** |
| クラス限定 | いま `cmd_add --teacher` は無条件で `classes=["*"]`（`server/tube_server.py:742,763`）。「担当クラスだけ読める」は文書の中だけの話で、実際は講師1人＝全50人。**ここを直さない限り、被害範囲の議論に意味がない** |

### 問い2：NASか、直結PCか

**どちらでもありません。ドイツのVPSに置き、NASはバックアップの受け先だけにします。**

依頼者の「NASを外部アクセスさせていいのか」という懸念は**結論として正しい**のですが、理由が違います。**NASが弱いからではなく、鍵と錠を同じ箱に入れることになるからです。**

この設計の中核は、進捗（サーバ）と氏名の対応表（講師の手元）が**別の場所にある**ことです。校舎の共有NASは、その対応表 ── 生徒名簿・保護者連絡先・授業料記録 ── が実際に置かれている場所である可能性が極めて高い。同居させれば**1回の侵入で両方が同時に落ち、氏名を持たない設計の価値がゼロになります。**

補足として、NAS本体のリスクも実測値で見る価値はあります。

| 事例 | 内容 |
|---|---|
| DeadBolt（QNAP、2022〜） | 全世界2万台超が感染 |
| Qlocker（QNAP、2021） | バックアップ機能の脆弱性を突き、1か月で約35万ドルを集めて撤収 |
| CVE-2024-10443（Synology、2024） | Photos のゼロクリック・未認証・root。**ポート開放していなくても QuickConnect 経由で到達した** |

侵入口はどれも**自作アプリではなくNAS本体のWebスタック**です。Tubeのコードをどれだけ堅くしても、同じ箱にDSM/QTSが載っている限り攻撃面は減りません。

| | 費用/月 | 校舎の停電・回線断 | 攻撃面 | 氏名対応表との分離 | 判定 |
|---|---|---|---|---|---|
| NASをポート開放 | £0 | 直撃 | DSM/QTS全体 | **壊れる** | 却下 |
| NAS＋トンネル | £0 | 直撃 | DSM/QTS全体（減らない） | **壊れる** | 却下 |
| 直結PC（最小Debian）＋トンネル | £0＋電気 | 直撃 | sshd＋Python のみ | 保たれる | Plan B |
| **ドイツのVPS＋Caddy** | **約£5** | **無関係** | sshd＋Caddy＋Python | **保たれる** | **推奨** |

依頼者の「PCだと不安、NASのほうが安心」という直感は、実は逆です。決め手は機種ではなく**その箱に他に何が載っているか**で、何も載っていないPCの攻撃面はNASよりはるかに小さい。ただし直結PCは電源断・回線断・機器故障・盗難がすべて直撃し、「誰がこの箱を見るのか」問題（ファン・ディスクの予兆を誰も見ない）が残ります。VPSはそれをまるごと切り離せます。

```
  生徒のスマホ／保護者のPC
        │  HTTPS
        ▼
  ┌────────────────────────────────────────┐
  │ Hetzner CAX11（ドイツ Falkenstein）      │  ← アプリとデータ
  │  Caddy → Python標準ライブラリ / systemd    │
  │  Hetznerの自動バックアップ（GUIで丸ごと復元）│  ← 非技術者の復旧手段
  │  毎晩 tar | age で暗号化1ファイルを吐く     │
  └────────────────────────────────────────┘
        ▲  毎晩、NASが「引きに行く」（読み取り専用の鍵）
        │  引くのは暗号化済みファイルだけ。中身はNASでは開けない
  ┌────────────────────────────────────────┐
  │ ロンドン校のNAS                          │  ← 外向きポートはゼロ
  │  暗号化ファイルを14世代保管                │     QuickConnect 無効
  │  毎晩、復元テストを1回して結果をメールで送る │  ← 唯一の監視系
  └────────────────────────────────────────┘

  氏名とIDの対応表 ＝ 紙。校舎の施錠場所に2部。
  上のどの箱にも、どのクラウドにも、絶対に載せない。
```

**前案からの重要な訂正：** 前案は `rsync` で `data/` を**平文のまま**NASにミラーする手順を書いていました。そこに入るのは進捗だけでなく、講師のパスワードハッシュ・全トークン・ログイン元IPを含む監査ログ・入室コードのハッシュです。つまり毎晩、氏名対応表と同じ建物・同じネットワークに全データの平文複製を置くことになる。**NASへ渡すのは age で暗号化した1ファイルだけにします。** これで security の指摘のうち3件（平文ミラー／入室コードの復元／IPの流出）が同時に消え、ops の指摘（rsyncのフラグ固定・`--delete` の暴走・resticのパスフレーズ・DSM更新でEntwareが消える）も全部消えます。

**Plan B（本部がEU外部ホスティングを認めなかった場合）：** 普段使っていないPCに最小Debianを入れ、Cloudflare Tunnel で公開。認証・同期・バックアップの設計はそのまま流用できます。条件は3つ：UPSを入れる／LUKSでフルディスク暗号化する（盗難＝そのまま漏えい）／故障時に誰が現地に行くかを先に決める。

**却下したもの：** Tailscale Funnel（公式に本番非推奨・URLに tailnet 名が露出）／ngrok（全訪問者に警告画面が出る。保護者に「この警告を無視して進んでください」と教えることになり、フィッシング耐性の教育として最悪）／Supabase（無料枠は7日無操作で停止。夏休みで確実に止まり、新学期初日が「動かない」から始まる）。

## 2. 公開前に必ず潰す穴 ── ここが終わるまで1人にも配らない

前案に無かった、または軽く扱われていたものです。**この節は他のどの節よりも優先します。**

### 2-1. 入口B（無認証＋氏名入力）を削除する ── 最優先

`app/js/ui.js:271-330` に、サーバに繋がらないときの経路が実装済みで、動きます。

```
boot() → probe() が失敗 → go('gate')
       → 「クラスコードを入力」（LDN-J2A）
       → 「はじめての人はここに名前」 placeholder「山田 太郎」
       → TubeStore.addStudent(名前, ...) が氏名を localStorage に平文保存
```

さらに `app/curriculum.js:86` の `teacherCode:'LDN-STAFF'` とクラスコード（`:75-78`）は、`curl https://<ホスト>/curriculum.js` で誰でも読めます。これを入口Bに打つと `ui.js:295` で `isTeacher=true` になり、講師画面に入れます。オフライン経路なので読めるのはその端末内のデータだけですが、**共用の保護者PCや教室の共用機ではその端末の全生徒分**で、管理タブの `ui.js:1497` `downloadText(exportBundle(all))` で全件JSONに落とせます。

攻撃は「同じWi-Fiでそのホストへの到達を数秒遅らせる」だけで成立します。電波の悪い場所でも同じ画面が出ます。

**「氏名を一切保存しない」という設計の中核主張が、いまのコードの中で偽になっています。**

やること：

- `viewGate` / `gateStep` / `gateClass` と、そこから呼ばれる `TubeStore.addStudent` 経路（`ui.js:330`、`ui.js:1526`）を**削除**
- `app/curriculum.js` から `code` と `teacherCode` を削除
- `TubeStore.addStudent(label, ...)` の `label` 引数を廃止し、座席番号しか受け取れない形にする（次に触る人が復活させられないように）
- オフライン時は「登録済みの端末なら、そのまま解ける」だけ。未登録端末では入室カードの入力欄しか出さない
- `ui.js:1497` の**講師の一括書き出し（exportBundle(all)）を削除**（そのPCがiCloud/OneDrive同期下だと、そこで国外移転と処理者追加が発生する）

### 2-2. 座席番号を五十音順から切り離す

日本の塾・学校の出席番号は姓の五十音順です。つまり `中2A-01..12` の並びは**名簿の並びそのもの**。侵入者が1人でも実名を知っていれば（自分の子、SNS、教室で見た1枚の紙）、前後の番号は名簿順から強く推定でき、12人クラスなら数人で全員が特定されます。

「氏名を持たないから、漏れても『ある番号が51語やった』だけ」という中心主張が、この一点で大きく割り引かれます。

**対策：表示用の番号を五十音順と無関係にシャッフルして振る。** 対応は講師の紙の名簿にだけ書く。コストはほぼゼロで、これだけで再識別リスクが一段下がります。**費用対効果が最も高い1項目です。**

あわせて `server/tube_server.py:625` の `row = dict(a)` を修正します。個別指定の宿題が `students:[sid,...]` と `createdBy` をそのまま生徒に返すので、「この補習を受けているのは自分を含めて3人」が本人に見えます。12人のクラスでは誰が呼ばれたか即座に照合されます。**ランキングを却下した理由（実質的な晒し上げ）が裏口から成立しています。**

### 2-3. ログインでサーバを落とせる経路を塞ぐ

`hash_pw` は scrypt N=2^15,r=8 ＝ 約32MB/回。`ThreadingHTTPServer` は同時接続数を制限しません。`login_blocked()` のカウントは**失敗が完了してから**加算されるので、存在しないIDを200件同時に投げれば200スレッドが同時に32MBを確保して約6.4GB ── CAX11（4GB）は即OOM。`Restart=always` で再起動し、`FAILS` はメモリ上なので**試行制限が全部リセットされます**。認証不要・帯域ほぼゼロで、何度でも繰り返せます。

やること：

- ハッシュ計算にセマフォ（同時4本まで）
- `login_failed` を**着手前**に加算する（成功したら戻す）
- systemd に `MemoryMax=1G` / `TasksMax=200`
- `FAILS` を1分ごとに1ファイルへ書き出し、起動時に読む

### 2-4. 訂正と削除が、マージによって無効化されないようにする

前案は「三重書き込みのせいでサーバを消してもクライアントから復活する」という穴を正しく見つけて tombstone を要求しました。ところが同じ文書が導入する「新しい方が勝つ／max」のマージは、**まったく同じ復活バグをサーバ側に作ります。** 訂正APIでサーバの値を下げても、生徒の端末が次にpushした瞬間 max で元に戻る。3端末あれば3回戻ります。

**対策：生徒ごとに `epoch`（世代番号）を持つ。**

| 操作 | 動き |
|---|---|
| 通常のPUT | `epoch` が一致していればマージして受理 |
| 訂正・削除・入室カード再発行 | サーバが `epoch` を +1 |
| 古い `epoch` の差分が来た | **マージせず拒否**し、`{reset:true, epoch:N, state:{...}}` を返す |
| クライアントが `reset` を受けた | localStorage / sessionStorage / IndexedDB の3ストアと端末トークンを消し、サーバの状態で作り直す |

これで Art 16（訂正）と Art 17（削除）が実際に効きます。tombstone だけでは足りません。

### 2-5. マージの入力検証を、マージ関数と同時に書く

差分は生徒本人が自由に作れます。maxマージは単調増加なので、一度入った値は縮みません。1人が `cards` に100万キー入れれば記録は永久に肥大し、講師画面の集計もそれを読みます。8MBのPUTを繰り返せばディスクも埋まります。**「blobまるごと上書き」より攻撃面が広い変更なので、検証・上限・拒否を同じPRで書きます。**

| 対象 | 上限・検証 |
|---|---|
| `cards` のキー | `^[a-z0-9]+:[0-9]{1,5}$` かつ既知の教材名のみ。1生徒あたり **5,000件** |
| `cards` の値 | 8要素の数値配列。各要素に範囲。`due` は現在時刻±2年 |
| `day` の日付 | 過去400日〜未来1日 |
| 端末ID | サーバが登録時に払い出す（クライアントが決めない）。1生徒4本 |
| 1回のPUT本文 | 256KB |
| 拒否したとき | 400を返し、監査ログに1行。クライアントは行列を捨てない |

### 2-6. `?full=1` を作らない

前案は「一括取得の廃止はTOTPより優先」と書きながら、同じ節で `?full=1` を残すと書いていました。攻撃者はクエリを1つ足すだけです。**講師UIは個票をN回引けばよく、それがそのまま監査になります。**

監査ログの丸めも撤回します。現状（`server/tube_server.py:684-699`）は毎回 `read_class` が1行残るので、丸めるとフォレンジック上の後退になります。**一覧の読み出しは件数だけ記録し、個票の閲覧は毎回残す。**

### 3-2. `setup.sh` ── 1コマンドで作り直せること

## 4. 画面 ── 3タブのまま、中身を直す

### 4-1. タブは増やさない

前案は4タブにしていましたが、**小1〜3に「きょう」と「しゅくだい」の区別はつきません**（どちらも“やること”）。1画面の情報を減らす目的は正しいので、手段を「置き場所を増やす」から「カードを減らす」に変えます。`app/tools/check.js` の死んだボタン検査・44pxタップ領域検査を作り直すコストも丸ごと不要になります。

| タブ | 中身（上から） |
|---|---|
| **きょう** | ①保存警告（壊れている端末のみ）②**きょうのカード1枚**（72pxの数字・「はじめる」ボタン1つ）③宿題ブロック（期限・のこり・進捗帯。**常に同じ形**） |
| **きろく** | ①今月やった日（カレンダーの塗り）②やりきったしゅくだい（新しい順）③これまでのことば数 |
| **せってい** | ①利用者の切替（座席番号のタイル）②おうちの人へ（1枚・印刷可）③わたしのきろくを見る／けすようにたのむ／こまったときは④この端末のデータを消す |

**遅れているときも画面の形を変えません。** 前案は「遅れているときだけ きょうにも1行出す」としていましたが、**遅れている子の画面にだけ余分な行が出る＝画面の形が変わること自体が恥の信号**になります。宿題ブロックは常に「のこり N ことば ／ ○月○日まで」の同じ2行で、赤くもしない。

### 4-2. いまのコードにある「正直に答えると罰が下る」を消す ── 配布前に必須

`app/js/homework.js` の `grade()`:

```js
if(g >= 3) s.done[key] = 1;
else delete s.done[key];        // ← ここ
```

一度覚えた番号で正直に「まだ」を押すと、**宿題の達成率が下がります**（100%→98%）。さらに `recompute()` が `s.completedAt = null;` に戻すので、**提出済みの宿題が未完了に戻り、講師画面の表示も戻ります。**

残したまま配ると、子どもは数日で「かんたん連打が得」を学習します。**ガチャを却下した理由（報酬が出やすい押し方を学習し、SRSの土台が崩れる）と同じ害が、すでに実装の中にあります。**

- `delete s.done[key]` を**削除**。`done` は「一度3以上を押したら立つ」フラグにする（復習の間隔は `p.cards` 側で別に管理されているので、これで壊れるものは無い）
- `completedAt` を粘着に（一度立ったら消さない）。表示は「提出ずみ・ふくしゅう中」

### 4-3. セッションが終わらない問題を消す

`app/js/ui.js:610, 712, 764, 825`:

```js
if(g === 1){ S.wrong++; S.queue.push(item); S.total++; } else S.right++;
```

分からない子ほど画面右上の「3 / 8」が「4 / 14」に育ち、終わりが遠のきます。e_low に「8問5分」を入れても、この加算がある限り小1のセッションは収束しません。

- **`S.total++` を削除。**分母は最初に決めたら動かさない
- 「まだ」の問題は末尾に積んでよいが、**同一問題は1セッション2回まで**
- 分母が動かないので、進捗帯が右に進み続ける＝終わりが必ず見える

### 4-4. 終了画面から点数を消す

`showDone()` は72pxの巨大数字で `S.right`（正解数）を出し、下に「N問中」、その直後に「残り40語・あと3日」を出します。

**設計方針は「褒めは1日1回だけ」「正答率は保護者に渡さない」なのに、子ども本人が毎回見る最大の数字が正答率そのもので、やり終えた瞬間に借金を見せています。**

```
   before                     after
   ┌──────────┐         ┌──────────┐
   │ おつかれさま │         │           │
   │           │         │  きょうのぶん、 │
   │    17     │   →    │   おわりました  │
   │  22問中・8分 │         │           │
   │ 残り40語   │         │    8ふん     │
   │ あと3日    │         │           │
   └──────────┘         └──────────┘
      [今日の画面へ]              [おわる]
      [つづける]                 つづける（小さく・ghost）
```

- `S.right` / `S.total` / `S.wrong` の表示を削除（内部では持ってよい）
- 残り語数・期限を終了画面に出さない（「きょう」タブに戻れば同じ形で見える）
- 「つづける」は ghost ボタンで下に。大きな塗りボタンで続行を促さない

### 4-5. 「きょうのぶん」を宿題に存在させる

`pace().perDay` は「残り÷残り日数（下限5）」の**都度再計算**です。3語やって中断し、同じ日に開き直すと、また5語以上を要求されます。保護者PCを短時間しか借りられない子＝まさに小学生は、その日のノルマを終えた状態に到達できません。

**設計上の唯一の肯定的ナッジ「きょうのぶん、おわりました」が、主活動である宿題で発火条件を持っていません。**

- その日の最初に `perDay` を計算し、**`hw[a.id].plan["2026-09-14"] = 6` として固定**する。同じ日は何度開いても6のまま
- 6問終えたら「きょうのぶん、おわりました」が出る
- `plan` は日付キーなのでマージ規則にそのまま乗る

### 4-6. 1日量の上限を、宿題にも効かせる

`TubeHomework.queue()` は `due()`（復習）を**無制限に**先頭へ積み、新出だけを `perDay` で切ります。`maxRev` も「1セッション8問」も読んでいません。`curriculum.js` に `e_low` / `e_high` を足しても、主活動である宿題には適用されません。**小1が「今日は50問」を突きつけられる経路が残ります。**

```js
function queue(p, a){
  var lv  = C.levels[p.level] || {};
  var pc  = pace(p, a);
  var rev = due(p, a).slice(0, lv.maxRev || 60);      // ← 復習も切る
  var nw  = fresh(p, a, pc.perDay);
  return rev.concat(nw).slice(0, lv.sessionMax || 20) // ← 1セッションの上限
            .map(...);
}
```

| 段階 | 対象 | 1日の新出 | 復習上限 | 1セッション | 文言 |
|---|---|---|---|---|---|
| `e_low` | 小1〜3 | 4語 | 20 | 8問・約5分 | ひらがな主体、小3までの漢字 |
| `e_high` | 小4〜6 | 6語 | 40 | 12問・約8分 | ひらがな主体 |
| `j1〜j3` | 中1〜3 | 現状のまま | 現状のまま | 現状のまま | 現状のまま |

**1日2回まで、はやめて1日1回にします。** 冊子を出して番号を探して開いたまま保つのは小学生が自力でやることではなく、実質「保護者が横で本を持つアプリ」です。所要は5分ではなく準備込み10〜15分。1日2回は保護者を1日2回拘束します。

段階は学年から自動導出せず、**アカウント作成時に講師が3段階から選びます**（中学生でも英語が初学なら `e_high` が適切な子がいる）。

## 5. 同期 ── 要求2は現状ゼロ点

### 5-1. リアルタイム（WebSocket/SSE）は不要

実際の使い方は「PCで解く→閉じる→別の日にスマホで解く」という逐次利用で、同一生徒が2端末を**同時に**操作する場面がありません。遅延を1秒から0.1秒に縮めても誰も得をしない一方、サーバは1接続＝1 OSスレッドを常時占有し、iOS Safari は背景タブを凍結して結局張り直しになります。

**目標値：前景に戻った瞬間に1秒以内でpull／解答から数秒でpush／開きっぱなしの画面は30秒で追いつく。** これで要求2は満たせます。

### 5-2. いま壊れている3点

| # | 現状 | 何が起きるか |
|---|---|---|
| 1 | PUTが409を返すと、クライアントは**その項目を送信待ち行列から削除**し、ローカルの進捗を全消去してサーバの内容で置き換える | **オフラインで解いた20問が、サーバにもローカルにも残らない。しかも生徒には何も表示されない。**「同期がまだ弱い」ではなく「既に壊れている」 |
| 2 | 進捗のpullは**ログイン時の1回だけ**（`ui.js:1573` の `visibilitychange` は宿題一覧しか取り直さない） | **要求2が成立しない。**毎回ログインし直さない限り、別端末の学習は反映されない |
| 3 | 衝突判定が「保存時刻が新しいほうが勝つ」の1行。しかもその時刻はクライアントの `Date.now()` | 時計が進んだ端末が**永久に勝ち**、遅れた端末は**永久に負ける** |

加えて、採点1回ごとに**最大95KBの全文**を送っています（30問で最大2.85MB/セッション）。校舎LAN内なら気づきませんが、外に出した瞬間に子どものモバイル回線で詰まり、**末尾の数問が最も失われやすくなります。** さらに画面を閉じる瞬間の送信（`keepalive`）は本文64KB上限なので、95KBの全文は**閉じ際に送れません**。

### 5-3. 2段階で直す（1つのPRにまとめない）

**段階A：喪失を止める（データ構造を変えない）**

`blob` は既にJSONオブジェクトなので（`store.js` の `serialize` の出力）、サーバはそのまま解釈できます。

- サーバが `cards` と `hw` を**項目単位でマージ**して受理する。**409を返さない**
- スカラ（`xp` `streak` `best` `hist` …）は当面いままで通り「新しいほうで上書き」
- クライアントの409分岐と「全キー削除→remoteで置換」を削除
- 差分PUT（`cards` と `hw` の変更キーだけ）＋ `pagehide` で `fetch(keepalive:true)`
- pullの起動条件を足す

これで**要求2が満たされ、喪失が止まります。**

**段階B：スカラを導出値に変える**（段階Aが2週間安定してから）

```
{
  v:2, sid, level, classId, epoch,
  cards: { "grit2500:1004": [iv, ef, due, reps, lapse, seen, known, g] },
  day:   { "2026-09-14": { "A7K2": {n, ok, nw} } },      // 日 → 端末ID → カウンタ
  hw:    { "ae9ddfa9d": { s:開始, c:初回完了, plan:{"2026-09-14":6} } },
  base:  { xp:0 },                                        // v1からの繰り越しのみ
  meta:  { started }
}
```

`xp / streak / best / lastDay / dayKey / newToday / sessDone` が `day` ひとつに畳まれ、**端末間でずれる余地が原理的に消えます。**

前案は「実生徒データが入る前の、いましかない窓」と書いていましたが、これは誇張でした。**50ファイル・4.6MBの移行スクリプトは20行でいつでも書けます。**作られた締切で、本当に急ぐもの（喪失修正）と急がないもの（構造刷新）を1つの塊にすると、両方が遅れます。

### 5-4. マージ規則（Python 約80行）＋ epoch ＋ 検証

| 対象 | 規則 |
|---|---|
| `cards` | 項目ごとに `seen` が新しい方。同値なら `reps`、次に `due`、最後に**JSON文字列の辞書順** |
| `day` | (日, 端末ID) ごとに各フィールドの `max` |
| `hw` | `s` `c` はそれぞれ非nullの `min`。`plan` は日付ごとに先に入ったほうを保持 |
| `base` | `xp` は `max` |

この4規則は**可換・結合的・冪等**です。順序が入れ替わっても、二重送信されても結果が同じ。**再送を恐れなくてよくなることが実質的な価値です。**

同値時の扱いを詰めないと可換になりません。`seen` が同値のカードで比較を打ち切ると `merge(a,b)` と `merge(b,a)` が食い違い、端末ごとに違う状態へ収束します ── しかも滅多に起きないので気づけません。**最後にJSON文字列の辞書順まで落として全順序にすること。**

`epoch` の扱いと入力検証は §2-4、§2-5 の通り。

**加えて、受理した差分を30日ぶん追記保存します**（1日数十KB）。マージ関数の微妙なバグは数週間気づかれず、その間バックアップは壊れた状態を14世代ぶん忠実に複製します。差分が残っていればリプレイして作り直せます。**これはマージを入れる前提条件です。**

### 5-5. 新しいプロトコル

```
GET  /api/p/{sid}   If-None-Match: "17"
  -> 304                                    （変化なし・本文0バイト）
  -> 200 ETag:"18"  {srev:18, epoch:3, now:<サーバ時刻>, state:{...}}

PUT  /api/p/{sid}   {base:17, epoch:3, sentAt:<端末時刻>, delta:{cards:{…}, hw:{…}}}
  -> 200 {srev:19, now:…, behind:false}
  -> 200 {srev:19, now:…, behind:true, state:{…}}   ← 端末が持っていない変更があるときだけ
  -> 200 {reset:true, epoch:4, state:{…}}           ← epoch不一致（訂正・削除・カード再発行の後）
  -> 400                                            ← 検証に落ちた（行列は捨てない）

409 は返さない。
```

30問セッションの差分は**約2.7KB**（現在は最大2.85MB。**約1000分の1**）。64KBを超えないので、画面を閉じる瞬間に送りきれます。

**送信の起動条件：** 採点ごとに dirty へ積むだけ、1.5秒アイドルのデバウンス。ただし次は即時 ── セッション終了／10問ごと／画面が隠れたとき／`pagehide`／宿題完了時。セッション終了時だけ最大3秒待って「きろくを おくっています」を出し、超えたら待たずに進む。**子どもを待たせるスピナーを作らない。**

**取得の起動条件：** 前景復帰（前回から2秒以上経過時）／ウィンドウのフォーカス／`pageshow`（iOS Safari の bfcache 復帰。**これが無いとホーム画面から戻った子の端末が更新されない**）／オンライン復帰／登録直後／PUT応答が `behind:true`／前景中は30秒間隔。背景ではタイマーを止める。学習セッション中もpullしてマージしてよいが、**出題キューは組み直さない。**

### 5-6. 時刻の権威をサーバへ移す

`due` は絶対時刻なので、時計のずれは復習スケジュール**そのもの**を壊します。3日進んだ端末で1週間オフライン学習すると、正しい端末から見て**3日間ひとつも復習が来ません。**

- **クライアント**：応答の `now` と自分の `Date.now()` の差を skew として保持し、`Tube.now()` を作る
- **サーバ**：差分の `sentAt` から drift を求め、5分を超えていたら差分内の全時刻を一律に戻す
- **`dayKey` を `Europe/London` 固定にする**（`app/js/srs.js:85`）。現状は端末ローカル時刻なので、日本から来たばかりでJST設定のままの端末は**9時間早く日付が変わり**、宿題の残り日数も講師の見え方とずれます。ロンドン校なのに「今日」の定義が端末任せになっている
- 12時間を超えるずれは週報に出す（隠さず現実世界で直させる）

### 5-7. 講師画面：要約インデックス

現状の `GET /api/class` は担当クラス全員分のブロブを丸ごと返します（**最大4.6MB**）。

- マージ受理時に `data/index.json` へ 1人約250バイト（sid・座席番号・進捗率・期限超過・skew・宿題ごとの達成数）を書き出す。50人で約15KB
- 個票は開いた1人分だけ `GET /api/p/{sid}`。これが講師アカウントが漏れたときの被害を実際に小さくする唯一の手段
- **`?full=1` は作らない**（§2-6）

### 5-8. オフライン時に生徒に何を見せるか

| 状況 | 表示 |
|---|---|
| 通常 | 表示なし。せっていに「さいごに おくったのは 10:24」の1行 |
| オフライン | 細い1行「いまは オフラインです。れんしゅうは できます。あとで じどうで おくります。」 |
| 未送信あり | せっていに「まだ おくっていない ぶん: 12もん」と「いま おくる」ボタン。**飾りにせず、押したら本当に送る** |
| 3日以上つながっていない | **子どもには出さない。週報と講師画面に出す** |
| 保存自体が壊れている端末 | オフラインより重い。**学習を始める前に**出す |

宿題ブロックはオフラインでもキャッシュを出し続けること。電波が切れた瞬間に宿題が消えたように見せない。

### 5-9. 検証（この7本が通るまで本番に出さない）

1. 端末Aで20問オフライン → 端末Bで5問オンライン → Aが復帰 で、**25問すべてが残る**
2. マージ関数に同じ差分を3回流して結果が変わらない（冪等）
3. 2つの差分を順序を入れ替えて適用して結果が一致する（可換）
4. 時計を+3日ずらした端末の解答が、補正後に正しい `due` を持つ
5. 5秒ごとにハードキルするサーバに対して30問解き、1問も失われない
6. **`epoch` を上げた直後の古い差分が拒否され、クライアントが3ストアを消して作り直す**
7. **不正な差分（キー10万件・未来日付・型違い）が400で拒否され、送信待ち行列が消えない**

`app/tools/check.js` はブラウザのコンソールに手で貼る運用なので、依頼者以外は誰も走らせません。**上の7本は `node` で単体実行できるファイルにして、リポジトリに置きます**（Pythonのマージ関数はサーバのCLIサブコマンドで走らせる）。回帰の門になるのはそちらだけです。

## 6. 法務 ── 実際に効く6つに絞る

前案は書類8点を公開の前提条件にしていました。現実の失敗形は「書類が終わらないので書類なしで配る」です。**法的に効くのは以下で、これ以外は優先度を落とします。**

### 6-1. 大前提：氏名を持たなくても法の外には出ない

いまの設計は**仮名化（pseudonymisation）**であって匿名化ではありません。UK GDPR Art 4(5) の定義そのもので、鍵（対応表）を持つ塾にとっては永久に個人データです。

**日本の実務感覚から最も踏みやすい地雷がここです。** 日本の「仮名加工情報」は開示請求・利用停止請求の対象外になるなど義務が軽くなりますが、**UKの仮名化にはそのような減免が一切ありません。**「氏名を消したから軽い扱いでよい」と整理すると、保護者からの開示・削除請求に応じられず違反します。しかも「氏名がないので個人データではありません」と通知に書くと、それ自体が**虚偽の透明性情報**として Art 5(1)(a) 違反が上乗せされます。

**では氏名非保持は無駄か ── まったく違います。** 仮名化は Art 25・Art 32 の適合措置として明示的に評価されます。その価値は「**氏名対応表を絶対にサーバ機に置かない**」という一点を守れるかで決まり、これがNAS相乗りを却下した本当の理由です。

**ただし、Art 34(3)(a)（漏えい時の保護者への個別通知の免除）を先に結論として書くのはやめます。** 免除は「データを判読不能にする措置」を要求し、管理者自身が鍵を持ち、12人クラスで座席番号が再識別に効く仮名化データがこれを満たすとICOが認める保証はありません。認められなかったとき、「事前に保護者へ通知しない結論を用意していた」文書が手元にあるのは調査で不利にしか働きません。**判断基準（何が漏れたら何を見て判断するか）は書いてよい。結論は書かない。**

### 6-2. 法的根拠は「同意」ではなく「正当な利益」

| | 同意 Art 6(1)(a) | **正当な利益 Art 6(1)(f)** |
|---|---|---|
| 撤回 | いつでも可能。撤回された瞬間に宿題管理が成立しなくなる | 撤回で崩れない |
| 13歳未満 | **親権者性の検証義務**（Art 8(2)）。メールを持たない設計と正面衝突 | 発動しない |
| ICOの見解 | 教育文脈では不適切（塾と生徒の力関係の不均衡） | EdTechで第一に挙げる選択肢 |
| 代償 | — | Art 21 の異議申立権が必ず付く |

**サービスの根幹を、撤回可能な根拠に乗せてはいけません。** 異議が出たときの動作を**先に決めておくこと**（サーバ保存を止めてローカルのみで学習継続、講師側には提出/未提出のフラグだけ残す）。実装しておけば、異議が来てもサービスを止めずに済みます。

**加えて、子ども本人が「やりたくない」と言ったときの経路も要ります。** Art 21 は保護者の権利ですが、子ども自身が使いたくないのに記録が残り講師が見続けることへの説明と停止手段が無い。**「おやすみ」（§4-7）をその受け皿にします。**

**④を書くこと自体が最大の信頼形成であり、同時に約束として自らを拘束します。**

### 6-6. 保持期間 ── 初年度は自動削除しない

**方針：在籍中＋卒塾後12か月 → 削除。監査ログ12か月。トークンは失効と同時に削除。**

**書いただけで実行されない保持方針は、通知を虚偽にするので何もないより悪い。** ICOの調査で最初に確認されるのは「方針と実態の一致」です。

ただし**初年度は自動削除ジョブを走らせません。** 無保守のcronが毎晩子どもの記録を消しに行く構図は、バグったときに取り返しがつきません。**削除候補の一覧を週報に出し、講師の確認後に実行**する。方針の履行は保たれ、対応表を持つ人間が最後に目で見る経路が挟まります。

**あわせて塞ぐ穴：** localStorage + sessionStorage + IndexedDB の三重書き込みが残っている状態でサーバ側を削除すると、次回同期でクライアントから復活します。**`epoch` の仕組み（§2-4）がこれを解きます**（削除時に epoch を上げ、古い差分は reset で弾かれ、クライアントが3ストアと端末トークンを消す）。これがないと「消しました」と保護者に伝えた内容が事実でなくなり、単なるバグではなく **Art 17 違反かつ虚偽説明**になります。

### 6-7. 訂正の経路（Art 16）

「講師は読めるが書けない」は完全性の観点では優れていますが、**Art 16 の履行手段が無い**ことを意味します。請求が来たときに「技術的にできません」は通りません。管理者権限でのみ実行でき、**必ず `epoch` を上げ**、監査ログに「誰が・いつ・何を・なぜ」を残す訂正機能を1本だけ作ります。

### 6-8. 外部通信ゼロを機械的に証明する

素のJSでビルドなしという構成の利点を、証明可能にしてください。フォント・アイコン・CDN・解析タグ・外部画像への参照が1件もないことを、CSPと**実際のネットワークログの両方**で確認し、結果をDPIAに添付する。AADC基準9（Data sharing）と基準10（Geolocation）を同時に満たす証拠になります。

### 6-9. その他の再識別ベクタ（AADC基準8）

- **座席番号のシャッフル（§2-2）** ← 最も効く
- 学習ログの時刻は分単位に丸める（**秒単位の学習ログは行動指紋になる**）
- 監査ログには表示名ではなくsidだけ、**IPは書かない**
- journald に `MaxRetentionSec=7d`、Caddy の access log は `discard`

### 6-10. 将来の機能追加が一気に地雷になる構造

いまの設計（氏名なし・メールなし・位置情報なし・ランキングなし）は、ICOの規範に**例外的によく合っています。** この適合性を壊さないことが、以後の制約になります。

| 足したくなるもの | 発動するもの |
|---|---|
| プッシュ通知 | 基準13＋夜間配信 |
| ランキング・他生徒との比較 | 基準5・基準9。**モチベ施策で最も衝突しやすい** |
| 学習解析の外部送信 | 基準9＋国外移転 |
| 決済・氏名の追加 | 設計方針そのものの崩壊 |

| 低学年が「まだ」を押すか | **冊子の答えが目の前にある状態で7〜8歳に自己採点させると、ほぼ「覚えた」になります。**歪みの主因は保護者ではなく“答えが見える自己採点”。SRSの間隔計算を低学年に適用してよいかは、実測でしか分からない |
| 兄弟が同じPCでタイルを正しく選ぶか | PINを作らない判断の検証 |
| 中断・再開が本当に効くか | 保護者がPCを取り返す頻度 |

**低学年でSRSが成立しないと分かった場合の逃げ道：** `e_low` は間隔反復をやめ、「今日の6語 → 3日後にもう一度 → 1週間後にもう一度」の固定3段にする。中学生向けの中核ループをUI文言だけ変えて小学生に流用しない。

### 7-7. 保護者がURLに到達できなくなる経路を塞ぐ

ドメインに塾名を入れない方針（正しい）＋メールなし＋紙1枚。**紙を無くした保護者は検索でも見つけられず、履歴が消えていれば詰みます。**

**塾の既存の連絡手段（連絡網・配布物・入塾時の書類）にURLを載せる運用を先に決めてください。** 教室にも1枚掲示する。これは技術ではなく運用の1行ですが、無いと確実に問い合わせが来ます。

**ドメイン名に塾名も学年も含めないこと。** URLは保護者のブラウザ履歴・共有PCのオートコンプリート・スクリーンショットに残ります。

```python
TRUSTED_PROXIES = {"127.0.0.1", "::1"}

def peer_ip(self):
    direct = self.client_address[0]
    if direct not in TRUSTED_PROXIES:
        return direct                              # 直結。ヘッダは信用しない
```

## 11. 最後に

この設計の一番の資産は、技術的な堅さではなく **「持っていないもの」の多さ** です。氏名がない。メールアドレスがない。位置情報がない。ランキングがない。外部ライブラリが1つもない。単語データを持たない。

保守する人がいない前提では、これが直感に反して**最も腐りにくい**構成です（npmもpipも無いので、数年放置しても動く）。保護者への説明でも、ICOのDPIAでも、この「持っていない」リストがそのまま最強の論拠になります。

**ただし、いまのコードの中では、そのリストの1行目が既に偽です。** `app/js/ui.js:271-330` が氏名を受け取って保存します。Phase 0 の2番目にこれを置いたのはそのためで、**この1点だけは、他の何より先に終わらせてください。**

そして、この案が5年もつかどうかを決めるのは、マージ関数でもTOTPでもなく、次の3つです。

1. **ソースが機関の持ち物になっているか**（いまはiCloud 1箇所）
2. **`setup.sh` で作り直せるか**（OSの寿命・侵害後の再構築・移設が全部これ1つで解ける）
3. **週報が届いているか**（届かないこと自体を異常と定義する）

この3つが動いてから、コードに触ってください。逆順にすると、9月に動き始めて、次の春に静かに止まります。
