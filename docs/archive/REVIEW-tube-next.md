# 「Tube-Next」提案の評価

作成日: 2026-08-15
対象: Gemini Antigravity が `tube-schools-bu` を読んで出した仕様案

---

## 0. 全体の評価

**方向性は正しく、いま作ってあるものと大きくは矛盾しません。**
Zero-PII、生成IDでの認証、講師の担当別ダッシュボード、宿題の期限管理は
すでに実装済みで、提案はそれを追認しています。

一方で **4点、そのまま採ると壊れる箇所**があります。いずれも
「動かしてみると分かる」種類ではなく、**着手前に決めないと後戻りが大きい**ものです。

| | 提案 | 判定 |
|---|---|---|
| 1 | 教材（GRIT の見出し語・訳語）を Firestore に置く | **採らない**（著作権・費用の両方で破綻） |
| 2 | 進捗を `{status, score}` だけにする | **採らない**（忘却曲線が消える＝製品の中身が無くなる） |
| 3 | Flutter Web への全面書き換え | **急がない**（要件は現行の構成で満たせている） |
| 4 | XP・レベルアップ演出・バッジ・連続記録 | **要判断**（英国の子ども向け規範と、以前の方針に反する） |

採るべきものもはっきりあります。**CSV一括登録・論理削除（アーカイブ）・
tenant_id** の3つは、いま無く、250名の入れ替わり運用には必要です。

---

## 1. そのまま採るべきもの

### 1-1. CSV一括登録と論理削除 ―― これが一番効きます

入れ替わりの多い250名を、1人ずつコマンドで作るのは無理があります。
提案の指摘は正しく、いまの弱点そのものです。

- **CSV一括作成** … 学年・クラス・出席番号の表を渡すとIDとパスワードが一括発行される
- **アーカイブ（論理削除）** … 退塾してもログインだけ止め、記録は残す。
  物理削除すると「去年の同じ学年はどうだったか」が消える

### 1-2. tenant_id を最初から入れておく

いまは1校しかありませんが、**後から足すのは高い**。
全レコードに `tenant` を持たせておけば、2校目が来たときに設計を変えずに済みます。
コストはほぼゼロなので、入れておく判断でよいと考えます。

ただし注意点があります。**「開発者が100%のIPを持ち、SaaSとして他校にも売る」**
という前提を取ると、開発者は UK GDPR 上の**処理者（processor）**、学校が**管理者
（controller）**という関係になります。学校ごとにDPAが要り、事故時の責任分界も
変わります。技術ではなく契約の話なので、売る前に決める必要があります。

### 1-3. 講師の担当別ダッシュボード

実装済みです。ただし提案の **「View All Students トグル」は採りません。**
担当外まで見えるボタンを1つ置くと、いま実装した最小権限が無効になります
（この穴は先日実際に見つけて塞いだところです）。全体を見る必要がある人には
`--classes '*'` の別アカウントを発行する形にしてあります。

## 2. そのまま採ると壊れるもの

### 2-1. 教材を Firestore に置くと、無料枠が初日で溢れます

提案のスキーマはこうなっています。

```json
"curriculums": { "grit2500": { "word_id_1001": {"en":"abandon","ja":"を捨て去る"} } }
```

**問題は2つあります。**

**① 費用。** 実際に数えました（Spark 無料枠は読み取り 50,000回/日）。

| | 1人あたりの読み取り | 250人の合計 | 上限に対して |
|---|---|---|---|
| 教材をDBに置く（提案） | 207回 | **51,750回** | **103%（初日で超過）** |
| 教材を静的ファイルに置く（現行） | 10回 | 2,500回 | 5% |

宿題50語＋復習150項目を1件ずつ読むと、それだけで1人200回に届きます。
**教材はDBに置かず、アプリと一緒に配るのが正解**で、これは現行の構成です。
20倍の余裕が生まれ、キャッシュの作り込みも要らなくなります。

**② 著作権。** `"en":"abandon","ja":"を捨て去る"` は、まさに市販単語帳の
**見出し語の選定と訳語**です。これはHANDOVER 4章が繰り返し警告している範囲で、
「開発者が100%のIPを持ってSaaSとして販売する」となると、他人の編集著作物を
自分の商品として売ることになります。

現行は**番号だけを持つ**方式で回避しています（生徒は冊子を見て自己採点）。
提案はこの回避策を無効化してしまいます。

### 2-2. 進捗を `{status, score}` にすると、忘却曲線が消えます

提案のスキーマ:

```json
"progress": { "WAL_USER_001_HW_202608_01": { "status":"completed", "score":95 } }
```

いま持っているのは、**項目ごとの間隔・易しさ係数・次回出題日**です。

```json
"en:v:reluctant:adj": [21, 2.5, 1785000000000, 4, 0, 1783200000000, 0]
//                     間隔  係数  次回          回数 忘れ 最終
```

「宿題が終わったか」だけを持つと、**間隔をあけて出し直す仕組みが成立しません。**
このアプリの価値は出題間隔の制御にあるので、ここを落とすと
ただの宿題チェックリストになります。

宿題の達成は**進捗の中の一部**として持てばよく、別テーブルにする必要はありません
（現行の `p.hw` がそれです）。

### 2-3. Flutter Web への全面書き換えは、いま急ぐ理由が薄い

提案の目的は「iOS / Android / iPadOS / Windows / macOS で動くこと」ですが、
**現行のWebアプリはすでに全部で動きます。**

| | 現行（素のWeb） | Flutter Web |
|---|---|---|
| 初回読み込み | 約100KB＋書体 | 1.5〜3MB（CanvasKit だとさらに） |
| 保護者PCの古いブラウザ | 動く | 描画が重い |
| 支援技術（読み上げ等） | 標準のHTML | 弱い |
| 書き換え量 | ― | **全部**（SRSエンジン、保存の堅牢化、宿題、講師画面） |

失うものが具体的です。**保存が消える不具合**は前身プロジェクトで最も長く
尾を引いた問題で、いまは6シナリオの検査で守っています。書き換えると
この知見はゼロからやり直しになります。

**Flutterが正解になる条件**は「App Store / Google Play に本物のネイティブアプリを
出す」場合です。そのときは改めて検討する価値があります。いまは違います。

### 2-4. XP・レベルアップ演出・連続記録 ―― 判断が要ります

2つの理由で、そのまま入れるのは避けたいところです。

1. **以前ご自身で「進捗とペース配分のみ、順位は出さない」と選ばれています。**
   XP・バッジ・レベルアップ演出は、その判断と逆方向です
2. **ICO の Age Appropriate Design Code は、子どもを長く留めるための
   仕掛け（nudge）を明示的に戒めています。** 英国で9〜15歳が使うサービスなので、
   連続記録の演出は適合性の審査対象になります。連続記録は
   「切れた瞬間に来なくなる」副作用も知られています

XPそのものは内部に持っています（`p.xp`）。**出すかどうかは表示の判断**なので、
決めていただければすぐ切り替えられます。

### 2-5. テストの「1問5秒」は、小4には速すぎます

漢字とアルファベットの読み取り速度が違います。9歳が問題文を読んで
選択肢を4つ比べるには足りません。**制限時間を設けるなら、
学年ごとに変えられる設定値**にすべきです（進度と同じ場所で持てます）。

## 3. Firebase を使うかどうか（置き場所の話）

提案の中で**唯一、真剣に検討する価値がある基盤の話**です。

**良い点**
- リージョンを `europe-west2`（ロンドン）に固定できる。UK GDPR の説明が楽になる
- バックアップ・TLS・可用性が込み。保守する人がいない前提に合う
- 無料枠で250名は収まる ―― **ただし教材をDBに置かない場合に限る**（上の表）

**引っかかる点**
- Google（米国事業者）との DPA が要る。リージョン指定は作成時のみで後から変えられない
- 無料枠にSLAは無い。学期中に止まっても文句を言う先が無い
- セキュリティルールを書き間違えると全公開になる事故が多い。
  いまの「サーバ側で判定する」構成のほうが、読んで確かめやすい

**結論**: 有力な候補ですが、**急ぎません**。
いまの構成は、置き場所を変えるのが `sync.base` の1行です。
先に決めるべきは `SECURITY.md` 6章（本部のIT方針）で、そこが決まってから選べば十分です。

## 4. 250名にするために、いま直すこと

提案が想定する規模（50名 → 250名）で、現行がそのままでは壊れる箇所です。
**これは提案の指摘とは別に、こちらで見つけたものです。**

| | 症状 | 対応 |
|---|---|---|
| 講師画面 | 担当全員の進捗を丸ごと取得している。250名なら**1回の表示で23MB** | サーバ側で要約を作り、開いた生徒だけ詳細を取る |
| 同期 | 1問ごとに95KBの全文を送っている | 変わった項目だけ送る（差分） |
| 同期 | 衝突が「ブロブ丸ごと、新しい方が勝つ」。オフライン分が消える | **項目単位で合流**する |
| 同期 | 時刻がクライアント依存。時計がずれた端末が永久に勝つ | サーバの時刻を権威にする |
| 名簿 | 1人ずつコマンドで作る | CSV一括＋アーカイブ |

## 6. このレビューのあとに実装したもの（2026-08-15）

### 同期 ―― 項目単位の合流に作り替えました

提案の Firestore 移行とは別に、**現行の同期が壊れていた**ので直しました。
Firestore へ移っても同じ考え方がそのまま要るので、先に片づけています。

| | 前 | いま |
|---|---|---|
| 送る量 | 1問ごとに全文（最大95KB） | **変わった項目だけ**（数十バイト） |
| 衝突の解決 | ブロブ丸ごと・端末の時計が新しいほう | **項目ごと・答えた回数が多いほう** |
| オフラインの扱い | あとから同期すると**消えた** | 両方の学習が残る |
| 他端末の変更の検知 | ログイン時だけ | **画面に戻るたび**。見張りは66バイト |
| 時刻の権威 | 端末 | **サーバ** |

実測（同じ生徒を2端末が同時に触った想定）:

```
端末B（保護者PC）が 5問を同期     → rev 32  合流 5件
端末A（スマホ・圏外だった）が20問  → rev 33  合流 20件
サーバの中身: 端末A 20件 / 端末B 5件  → 両方残った
同じ項目を両方が触った場合 → 回数5のほうが残った（時計は無視）
```

**時計に頼らないのが要点**です。子どもの端末は時刻がずれます。
「答えた回数」は端末の中でしか増えず減らないので、時計が狂っても順序が壊れません。

### 教材 ―― 5科目に増やしました

`app/content/` に科目ごとのフォルダを置き、`manifest.js` に1行足すだけで
増やせる形にしてあります。**アプリ本体もサーバも触りません。**

| 科目 | 教材 | 項目数 |
|---|---|---|
| 英語 | IELTS コア | 1,894 |
| 理科 | 中1 | 22 |
| 社会 | 中1 地理 | 18 |
| 数学 | 中1 | 26 |
| 国語 | 漢字 小学校高学年 / 漢字 中学 | 21 / 16 |

理科・社会・数学・国語はすべて**書き下ろし**です（転記なし）。

`python3 app/tools/check-content.py` で教材を機械的に検査できます。
目録との食い違い・空欄・他言語の混入を見ます。
実際、この検査で**教材を書いている最中に紛れ込んだ他言語の断片35件**を捕まえました。
目で読むと必ず見落とすので、教材を足したら必ず通してください。
