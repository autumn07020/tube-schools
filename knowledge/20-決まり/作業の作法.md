# 作業の作法

## トークン
- 並列のエージェントで 2 度大損した（2026-08-09 に 70 万、09-11 に 120 万）。**単独が既定**。ultracode でも単独。並列は見積もりを示して了承の後だけ。
- 巡回は 1 回 10 万トークン以内。無為な作業で浪費しない。毎回同じ動作をしない。
- 短い確かめは Agent（subagent）でもよいが、長い仕事は独立したセッションにする。

## 進め方
- **指示の範囲内は聞かずに完了まで進める。範囲外・権限の拡張は提案して止まる**（2026-09-24）。
- 段ごとに止まらない（2026-10-08 の叱責「全然ダメ。背景のアニメーションからリキッドグラスから全く反映されていない」）。本人が見たいのは反映された画面。途中で聞くのはデータが壊れる・戻せない判断だけ。
- 「できない」と言われたら、まず何ができて何ができないかをコードで確かめてから答える。
- 作業の最後に `knowledge/90-種.md` へ気づきを 1 つ以上書き、効果大・手間小のものを 1 つ提案する。検査を 1 つ足したら種を 1 つ消す。
- 不具合・不変条件・文書の食い違いは了解なしで直してよい。

## チームと担当の線
- チームは 5 つ：コード・仕様（code）・デザイン（design）・運用・データ・デバッグ（ops）・法務・申請（legal）・資料（docs）。定義は `.claude/agents/<チーム>.md`、Mac での始め方は `/team-<チーム> 題`。クラウドでは分野ごとの routine（`knowledge/40-運用/routine.md`。指示文は `.claude/routines/`）が同じ定義で動き、その上に**リーダー**（routine「TUBE リーダー」。2026-10-31）がいる。本人が指示するのはリーダーだけ。リーダーが分野ごとの issue に分け、2 時間ごとと PR の出来事で進み具合を見て、直しを指示し、本人の手が要るもの（merge・決めること・Mac の作業）だけを番号で出す。6 本とも 1 つの会話が続く。知識は全チーム同じ（CLAUDE.md と knowledge/）。違うのは触ってよい場所と道具だけ。
- 起動時に `CLAUDE.md` と `knowledge/INDEX.md` を読む。セッション名は「チーム名-題」。
- **指示の入口はリーダーのチャット**（2026-10-31。本人が issue を直接立ててもよい）。issue は雛形（`.github/ISSUE_TEMPLATE/`）で立てると分野のラベル（コード・デザイン・運用・法務・資料）が付き、そのチームの routine が拾う。チームが付けるラベルは「対応中」「PR あり」。「保留」「本人」が付いた issue は拾わない（「本人」は本人の判断が要るもの）。ラベルの一覧は `.github/labels.json`（Actions「ラベル」が main でそろえる）。
- 1 つの issue ＝ 1 つのブランチ（`code/issue-N` のように `<チーム>/…`）＝ 1 つの PR。PR の 5 欄：何を・なぜ・検査・知識を更新したか・本番への影響（`.github/pull_request_template.md`）。PR を出したら issue に link をコメントする。
- 担当外の場所は触らず、issue に担当チームのラベルを足して渡す（自分のラベルは外す）。急ぎならセッション間のメッセージで知らせ、記録は issue に残す。
- クラウドのセッション（routine）では GitHub の GraphQL が使えない（`gh issue …`・`gh pr …` は 403）。REST（`gh api repos/autumn07020/tube-schools/…`）で読み書きする。`gh run list` は使える。
- チームの routine は見張り用の routine（reminder・scheduled task）を作らない（2026-10-21 に PR の見回りが重なって、アカウントの利用の上限に 6 回当たった）。PR の行方はリーダーが見る。
- 全チームを止める合図は、置き場の直下の `チームを止める.txt`（リーダーも止まる。巡回は `巡回を止める.txt`）。
- 決めたことはどのチームも `knowledge/70-決定録/YYYY-MM-DD-題.md` に 1 ファイル（決めたこと・理由・却下した案・影響）。
- GitHub は無料（2026-10-14 本人）。無料の私有リポジトリでは GitHub が main を守れない（赤でも merge できる・CODEOWNERS の承認は出ない）ので：main に直接 push しない（Claude のセッションは番人が止める）、merge は本人が PR の ✓ を見てから押す、検査が赤い PR は merge しない。flake は再実行で逃げず検査のほうを直す。

## 知識の書き方
- 1 ファイル 1 題。先頭の表（name・description・updated・owner・status）。事実と判断を分ける。数字には出典（検査名と日付）。英語を添えない。
- 古いものは消さず `knowledge/archive/`・`docs/archive/` へ（INDEX から外す）。
- 記憶（~/.claude の memory）は knowledge/ への指差しだけにする。新しい事実は knowledge/ に書く。
