## 2. 大目標

### 2.1 いまの大目標（北極星）

- **一講師として、ロンドン校の役に立つ。** 講師の時間を授業へ。生徒の宿題と成績の「あいだ」を仕組みで支える。
- 買い手は組織ではなく、**現場の講師と生徒**。組織のシステム（早稲アカOnline）と比べさせない。売り文句を作らない。
- **スロースタート・部分導入**が前提。使う講師だけ、使う教科だけ、使う深さだけ（§5.10 導入の段階 0〜4）。
  使わない講師には何も求めない。紙のクラスと半年以上混在しても便利であること。
- **壊れない・嘘をつかない・戻せる**を、機能の価値より先に置く。

プレゼンで使った一文（本人が決めた言い方。これより強く言わない）：
> 宿題と成績を、仕組みで後押しする。講師の時間をもっと、授業へ充てるためのご提案です。

- 組織のシステムとして売り込む／早稲アカOnline（組織の公式ポータル）と機能で比べる。

### 3.1 作り手

- 早稲アカ ロンドン校の**非常勤講師1名**（ワーキングホリデーの在留資格。本部の社員ではない）。コンピュータには強いが、開発は Claude Code に任せ、本人は**判断・確認・本番への反映**を受け持つ。
- 組織との**契約は無い。お金も受け取らない。**唯一の願いは「一講師である私のシステムを、ロンドン校で試験導入したい」。
- 本人の端末は Mac、ブラウザは **Safari**。原本は iCloud Drive の `tube-schools/`。前身の個人用アプリ `myenglish/` は本人が毎日使っているので**絶対に変更しない**。

### 3.2 組織から見たときの弱み（専務の5つの意見。反論しない）

| 意見 | 本当の意味 |
|---|---|
| ワーホリの人に任せるのはリスクしかない | 組織が依存してよい相手か。文書があっても解決しない |
| 早稲アカOnline で全部できている | 組織が必要とする層（お知らせ・出欠・模試成績・保護者窓口）はすでに満たされている |
| 講師の負担が増えるのでは | 新しい道具は最初は必ず負担を増やす。減る証拠は無い |
| 使わない講師・教科への批判になるのでは | 見えなかったものが見えるようになることへの警戒 |
| 宿題を管理させるのは正義か | 道具を売っているつもりで「宿題は管理すべき」という規範を売っていた |

→ この5つを**構造で**消す方向に作っている：使わない講師には何も見えない・何も求めない（導入の段階）、判断は講師に残す、未評価を講師の成績に見せない、など。

### 3.4 塾の制度（システム全体の周期を決めている）

- **5週周期**。組み分けテスト（α/β、T/R の入れ替え）と単元確認テストが35日ごと。**月や年の単位が出たら設計が外れている。**
- クラス：小4〜小6は α・β・K、中1〜中3は T・R（D は合同）、中3に土特・必勝。理科・社会などは学年合同。受講科目は生徒ごと（国英／国数英／国数／5科）。
- 教材は他社（四谷大塚の予習シリーズ等）と早稲アカ自社のもの。**中身は持たない**（番号・ページ・範囲だけ）。

### 3.5 法と倫理

- 英国（UK GDPR、ICO の子ども向け規範）。DPIA 草案・保護者向けの説明文あり（`DPIA.md`、`保護者むけ_個人情報の説明.md`）。
- **氏名・住所・電話・支払い情報をサーバに置かない。** 生徒は出席番号＋クラス＋ランダムな sid。誰かは講師の手元の名簿にしか無い。破られても流出するのは「ある番号が単語を51語やった」という事実だけ。
- **市販教材を複製しない**（語の選定・訳語・例文・問題文は編集著作物）。自作の問題は字種・単元の一覧（内閣告示で著作権の目的とならない）と事実だけを典拠にし、文はすべて自作。Wikipedia（CC BY-SA）は使わない。
- 順位を出さない（下位の子がやめる）。子どもを留める仕掛けを戒める規範を意識し、出すのは「続いた日数」と節目の祝いだけ。

## 4. 根本的なシステム構成

### 4.1 全体図

```
 生徒のスマホ・保護者の PC/iPad ─┐
 講師の PC・iPad（ペン）       ─┼─ HTTPS ─ Cloudflare ─ AWS Lightsail（ロンドン・Ubuntu・1GB）
                                 │                         tube_server.py（Python 標準ライブラリだけの HTTP サーバ）
                                 │                         /srv/myacady/ ← すべて JSON ファイル
                                 │                         S3 へのバックアップ（deploy/backup-setup.sh）
 本人の Mac（iCloud の原本）── sh deploy/更新.sh ──→ コードだけを送る（記録には触らない）
```

- **依存ゼロ**：Python 標準ライブラリだけ（追加パッケージ無し。PDF も PNG も純 Python で組む）、画面は素の JS と CSS、ビルド無し、外部 CDN 無し、CSP は `'self'` だけ。
  理由：一人で保守し、いつでも別のサーバへ移せ、誰かが引き継げること。部品が少ないほど壊れ方が少ない。
- **データベースを使わない**。校舎ごとのフォルダに JSON。1人の進捗は最大95KB、250人で24MB。控え（キャッシュ）で読み込みを吸収（300名で同期約4ms、講師の一覧25ms）。

### 4.2 設計の骨格（理由つき。別のサービスでもそのまま使える）

1. **教材と進捗を混ぜない。** 教材は全員共通・読み取り専用・アプリと一緒に配る。進捗は1人1ファイル。混ぜると教材を1語直すたびに全員分を書き換える。
2. **項目の ID は中身から作る**（`en:v:reluctant:adj`、`sci:t:光合成`）。配列の位置を使うと、1語挿しただけで全生徒の進捗がずれる（前身で実際に起きた）。科目コードは一度決めたら変えない。
3. **氏名を持たない。** 持たないものは漏れない。技術的な対策より効く。
4. **校舎（テナント）を完全に分ける。** パスは `server/paths.py` の外で組み立てない。生徒に関わる読み書きは `school` を**省略できない第1引数**に取る（省略できると、いつか省略される）。**校舎は合言葉（token）からだけ引く**。リクエストが名乗った校舎・ID を信じない。ファイル名は paths が許す一覧にあるものだけ。
5. **判定はサーバ。** 画面の出し分けは判定ではない（写真を受けるか、添削を返せるか、紙の宿題の経路 route も、サーバが教材や段階から引く。画面から届いた値を信じない）。
6. **発行のときに確定し、出したあとは書き換えない。** 生徒ごとの宿題の決まりも、出す瞬間にだけ当てる。出したものを書き換えると写真・評価と食い違う。前の評価も書き換えない（いつ誰が付けたかが消える）。
7. **派生値は保存しない。** 理解度は毎回組み立てる。講師むけの要約 `summary.json` は壊れたら作り直せる控えで、原本ではない。
8. **推測より明示。概念を増やさない。** 増やすなら既存の概念で置き換えられないか先に考える。誰にも追加入力をさせない（経路は教材の性質で決まる）。
9. **時計に頼らない。** 子どもの端末は時刻がずれる。同期の合流は「答えた回数」（減らない数）で決める。日付の比較は端末の暦で作る（`toISOString()` は世界標準時で、夏のロンドンでは夜0時台に1日ずれる）。

### 4.3 データの置き場

```
$MYACADY_ROOT/                 手元は server/data、本番は /srv/myacady
  index.json                   ログインIDと校舎の対応だけ（個人情報なし）
  tokens.json                  セッション（合言葉はハッシュで保存。生徒14日・講師12時間）
  shared/                      全校舎共通（取り込んだシラバスなど）
  schools/<slug>/              ここから内側は校舎ごとに独立（slug は ASCII：london / ny / tokyo）
    school.json  accounts.json  roster.json  curriculum.json（学年ごとの進度・毎日テストの範囲）
    lessons.json（コースと授業計画 plans。段階 use もここ） materials.json（教材台帳） assignments.json（出した宿題）
    submissions.json（写真の台帳）ratings.json（評価。生徒の記録とは別）messages.json
    personal.json（生徒ごとの宿題の決まり）presets.json scores.json（塾内テスト）
    insight.json（提案を出した・見送った）notes.json exams.json sheets.json weak.json
    summary.json（派生）audit.log（監査の跡）
    progress/<sid>.json        1人1ファイルの学習の進捗
```

- ログイン ID は校舎コードを頭に付けて全校舎で一意に（`lj2a01`）。同じ ID が2校舎にできると「入れるが宿題が出ない」という追いにくい壊れ方をする。
- パスワードは scrypt（無ければ pbkdf2 60万回。黙って弱いほうに落ちない）。試行制限あり。

### 4.4 画面（クライアント）

- 1枚の `index.html` と素の JS のモジュール：`ui-core.js`（土台・タブ・遷移・入口・見張り）、`ui-student.js`（生徒と保護者）、`ui-teacher.js`（講師のトップ・時間割・導入と進度）、`ui-desk.js`（宿題チェック・成績のコース・添削）、`sync.js`（API）、`store.js`（端末内の保存）、`srs.js`（出題の理屈。DOM に触らない）、`viz.js`（図。純粋な関数）、`cheer.js`（祝いの数え方。純粋な関数）、`photo.js`（写真を縮める）、`homework.js`、`omr.js`（紙のマークをカメラで読む）ほか。
- 端末内の保存は localStorage と IndexedDB の二重。**保存できるかは必ず実測で確かめる**（§8）。
- 複数の端末：`GET /api/rev` が台帳の更新時刻（数十バイト）を返し、25秒ごと・画面に戻ったとき・回線が戻ったときに、変わった台帳だけ取り直す。
- 配り方：js・css・svg は gzip＋ETag で 304。冷えた状態の総量は gzip で約236KB。API は `Cache-Control: no-store`。

### 4.5 API の地図（主なもの）

| 領域 | 口 |
|---|---|
| 入口 | `POST /api/login`・`/logout`、`GET /api/me`（役割・担当・受講科目・教科ごとの段階 `useBySubject`）、`GET /api/demo`、`GET /api/health`、`GET /api/rev` |
| 生徒 | `/api/p/<sid>`（自分の進捗だけ）、`/api/growth`（成績の伸び）、`/api/submissions/mine`、`/api/notices`（お知らせと「わかった／質問する」）、`/api/messages` |
| 講師 | `/api/today`、`/api/lessons/grid`（時間割）、`PUT /api/lessons/use`（導入の段階）、`/api/class/…`、`PUT /api/check/rate`（評価）、`/api/submissions/<aid>/<sid>/{print,pdf,scan,return}`（印刷・取り込み・添削を返す）、`/api/quiz`（提出箱）、`/api/insight/…`（理解度と提案）、`/api/personal`・`/personal/bulk`（生徒ごとの宿題）、`/api/presets`、`/api/scores`（塾内テスト）、`/api/assignments/…`（宿題・毎日テスト・総復習テスト対策）、`/api/curriculum`・`/materials`（進度と教材） |
| 運営 | `POST /api/roster/bulk`、`GET /api/hw/outbox`（保護者への連絡の書き出し。名前・点数を入れない） |

生徒は**自分の sid だけ**（`acc["sid"]` 固定）。講師は**担当コースだけ**（生徒を指す口は必ず在籍を確かめる）。全部を見る講師（`*`）以外に全校舎を渡さない。入力は長さと形を切ってから使い、数は `int()` して丸める。本文は 8MB（写真は12MB）まで。

## 5. 中核の概念（これが分かれば全部読める）

### 5.1 校舎・クラス・コース
- **コース＝クラス×教科**（例 `e4b:japanese` 小4β 国語）。担当講師・受け取る生徒・授業のコマ（曜日・時刻）・授業計画を持つ。宿題・成績・段階はすべてコース単位。
- コースと時間割は CSV で足し引きする（`courses-import`）。消さずに期間の終わりを入れる（出した宿題の行き先が浮かない）。時刻の無いコースも一覧から消さない。

### 5.2 シラバスと授業計画
- 「何をやるか」はコースが指す**シラバス**（`server/syllabus/<id>.json`。取り込んだものは `shared/syllabus/` が優先）から組む。単元は `label`（教材での呼び名：第3回／5章-3）と `topic`。**授業計画の回の番号と教材での呼び名は別の物**。
- 日付は anchor（その単元をやった週の月曜）の1点で結ぶ。前後は授業1回に単元1つ。総復習の回は教材が決める。
- いまの12コースのシラバスは**仮置き**（講師の記憶と学習指導要領から推定）。`provisional: true` と出どころを持たせ、画面に「仮の予定」と出す。

### 5.3 宿題と毎日テストを混ぜない
| | 宿題 | 毎日テスト |
|---|---|---|
| 必須か | かならず | 任意 |
| 期限 | ある | ない |
| 中身 | 講師が指定した単元・範囲（授業計画から自動で下書き→講師が直す） | 暗記だけ、10〜20分（SRS が自動で組む） |
混ざると「どれが必ずやるものか」が分からなくなる。1日の新出は **8〜12語が20分の現実的な上限**（数週間後には復習が1日150〜200問に育つ）。

### 5.4 紙とアプリの併走（いちばん大事な前提）
**紙9割の生徒とアプリ10割の生徒が同じ画面に並ぶ。** 素直に作ると、紙でちゃんとやっている生徒ほどシステム上は不真面目に見える。これが起きた講師は二度と使わない。
- 経路は**教材の性質**で決める（漢字の書き取りは誰が出しても紙、単語帳は誰が出してもアプリ）。宿題ごとに指定させない。
- 紙の宿題を「期限切れ」に数えない（アプリは観測していない。観測していないものを「やっていない」と言わない）。
- アプリで解く割合 `share` を数字に必ず添える。紙のカードに押せる要素を置かない。紙の宿題は期限から1週間で一覧から落とす。

### 5.5 束・提出・評価
- 1回の授業の紙の宿題は**束**（鍵 `lesson.key#n`）。生徒の提出は束に1回・写真1組（「まとめて提出」）。講師の評価も束に1つ。「出すだけ」の宿題は束に入れない。
- 評価は**1〜5**（5がいちばん良い）。講師は数字キーで付け、押した瞬間に保存。確認も保存ボタンも無い。同じ数字をもう一度押しても変わらない。消すのは 0。
- **生徒には数字を見せず言葉だけ**（よくできました／できました／もう少し／がんばろう／やり直してみよう）。
- **未評価は講師のやることの一覧にだけ出す。** 成績・理解度・提出率では「無い」として扱う（評価を付ける講師のクラスほど悪く見える作りにすると、誰も付けなくなる）。
- **仮の評価**：写真が出ているのに講師の評価が無いまま期限から7日過ぎたら、生徒・保護者・理解度では仮に「できました（4）」とみなす（講師の付け忘れで生徒が最低評価にならないように）。講師の画面では未評価のまま。

### 5.6 写真の往復と添削
- 生徒：撮る → 札にたまる → もう1枚／選ぶ／外す → 「N枚を送る」。写真は**必ず長辺1600px・JPEG 0.82 に縮めてから**送る（1枚300〜600KB）。
- 講師：宿題チェックの画面で写真を見ながら 1〜5 とひとこと。書いて返したいときは **iPad の画面で直接赤を入れる**（写真の上に canvas。線は写真の画素座標で持ち、返すときに原寸で合成）か、印刷して赤を入れて撮る。対面の生徒の紙は講師が取り込める。PDF にもできる。
- **提出箱**：授業内の小テストや作文を、授業計画とぶつからない番号の回として出す。あとは宿題チェックと同じ道。
- 写真は保存期間（既定180日）を過ぎたら消す。出した記録・評価・ひとことは残す。

### 5.7 理解度と提案
- 生徒×単元。根拠は 宿題の評価 0.45・塾内テスト 0.35・毎日テスト 0.15・対策の丸つけ 0.05 を、**あるものだけで割り直す**。無い根拠は重みごと外す。評価が無いのは 0% ではない。
- 保存しない。画面には必ず根拠を添える。70%未満は黄。四捨五入は half-up（Python の `round` は偶数に寄せるので画面の `Math.round` と1ずれる）。
- 提案は黄の単元にだけ。講師が出した・見送ったを残し、見送ったものは21日出さない。**解き直しを決め打ちで提案しない**（講師が登録したプリセットから選ぶ）。

### 5.8 生徒ごとの宿題
- 生徒×コースの**決まり**（出さない・減らす・置き換える・足す／この回だけ・次に変えるまで）。発行のときにだけ当てる。
- **プリセット**：講師がコースごとに登録した「教材＋段＋範囲の決め方」。まとめて80人まで出せる。「いま誰に何を出しているか」は1か所で見る。
- 変えるときは生徒への**ひとこと**を付けられる。生徒は「わかった」か「質問する」。質問のあいだその決まりは効かない。7日で自動で了解。
- 生徒の画面には「個別」の札を出さない（講師の画面にだけ「この生徒だけ」）。

### 5.9 毎日テスト（SRS）
- SM-2 の間隔反復。**教材データが要るのはここだけ**。教材を置けない場合の代わりは「ページ指示＋紙で解いて正誤だけ記録」（`server/genbank.py` の雛形。未配線）。
- 動機づけに点数と順位を出さない。出すのは続いた日数・今週の目標（週3日、小6と中3は週5日）・正答率の推移（端末の中だけで数える）。

### 5.10 導入の段階（スロースタート・部分導入の要）
コースごとに **0〜4**。講師の「導入と進度」タブで、学年ごと・教科ごと・1コースずつ、**押した瞬間に保存**。

| 段階 | 名前 | 効くこと |
|---|---|---|
| 0 | 紙のまま | 時間割にだけ出る |
| 1 | 宿題を出す | 授業計画の宿題が生徒の画面に出る。提出と評価は紙のまま |
| 2 | 写真で提出 | 生徒が写真で出せる（サーバも2未満なら受けない） |
| 3 | 添削まで | 赤を入れて返せる（3未満はサーバが返却を受けない） |
| 4 | 毎日テストまで | 毎日テストがその教科で出る |

- 積み上げ。**印の無い古いコースは 4**（動いているものを止めない）。「使わない→使う」で前の段階に戻る。
- 画面は「**表とはしご**」：行＝コース名・はしご（5段。今の段階まで塗る）・今の段階の言葉。言葉と説明は列の見出しに1回だけ。学年ごとに「まとめて」の行。

## 7. UI/UX の哲学

### 7.1 圧倒的なわかりやすさ
- 1画面に「**次にやる1つ**」を先に出す。大量のタスクを並べない。
- 見出しは**日本語だけ**。中身をそのまま言う短い名前。タブと同じ中身ならタブと同じ名前。英語を添えない（本人「カッコつける必要はない」）。
  いまの見出し：生徒＝今日やること・自分の記録・先生から・宿題・今週／来週・毎日テスト・設定。講師＝今日やること・時間割・成績・導入と進度。
- **動作だけを言う**（写真を選ぶ・数字を押す・赤を入れる・返す・足す）。抽象的な言い回し・臭いせりふは禁止（「赤ペン」「先生の目」「あたたかみ」の類。本人）。AI くさい言葉にしない。
- 数字には必ず根拠を添える。分からないものを 0 と出さない。「9/10人」と実数で。
- 小さな添え書きに頼らない。読む時間が無い前提で、**大きな文字だけで伝わるか**。
- 言葉の選び方：採点する（見てあげる、ではない）／まだ（遅れ、ではない）／未評価（評価まだ、ではない）／算数（小学）と数学（中学）を分ける／学年を二度書かない。
- 押す前に結果が分かること。押したら何が起きるかを1行で言う。

### 7.2 美しさ（Apple のウィジェットが手本。迷ったら apple.com を見る）
- **線を引かない。** 区切りは面と余白。面は、地との明度差・影（髪の毛ほどの縁 .5px＋近い影＋遠い影）・上辺の光で立たせる。行や入力欄には影を付けない。
  ```
  --bg:#EFEFF3  --surface:#FFFFFF
  --card-hi:inset 0 1px 0 rgba(255,255,255,.9)
  --card-shadow:0 0 0 .5px rgba(23,21,15,.07), 0 1px 2px rgba(23,21,15,.07), 0 12px 30px -14px rgba(23,21,15,.32)
  ```
- 色はワセアカの**青と黄だけ**。アプリの青 `--accent:#005BAC`（満ちた目盛りは #0A4F8F→#2E86D6→黄）、黄 `#F9B900`（ロゴの study と同じ）。資料では #004E93・#0A6FC7。
  黄は1本だけ持ち、面（accent2）・地（26%に薄めた soft）・字（#8A5A00。#F9B900 は白地で 1.6:1 で読めない）・線で役を分ける。**青＝進んでいる・選ばれている、黄＝今日・手を入れる所・祝う。それ以外は無彩色。**
  教科の色は薄いグラデーションだけ（国語＝赤とピンクの間、算数・数学＝青、理科＝緑、社会＝黄、英語＝緑と青の間）。達成の黄は濃い所を狭く、薄い面を広く。
- 地は iOS の壁紙のようなごく淡いグラデーション（左上に黄、右下に青 ―― 札の光の向きと同じ）。暗いテーマは自分で選んだときだけ（端末の設定では切り替わらない ―― 迷わせないため）。
- 角は大きく：札22px・紙26px・行16px・ボタン14px・入力欄13px。四角い印は iOS のアイコンと同じ 22.37% の比。
- 書体は端末のゴシック（Hiragino Sans／Yu Gothic UI／Noto Sans JP、数字は SF Pro の等幅数字）。明朝は使わない（道具に見えなくなる）。**絵文字・記号アイコンを使わない。** 階層は大小と余白で作る。
- 幅は **container query** で決める（画面の幅ではなく中身の幅）。行を端から端まで伸ばさない（760px で止める）。列番号を直に書かない。列の数は割り切れる数だけ。
- 図：点や棒に数字を振らない。数字は大きな1つ（最新）か、線の右端の「名前 最新の値%」だけ。横棒グラフを使わない。四角には凡例を必ず添える。**並びは1つに固定**（名前の順）―― 理解度で並べ替えると見る場所が毎回変わって読めない。
- 同じ概念は同じ見た目。新しい部品を作る前に、ある部品で書けないか。ホームの札と宿題タブの札は同じ中身。

### 7.3 手ざわりと動き
- **押せるものは必ず押せる。** 押せそうで押せない要素を作らない（機械的に検査する）。当たり判定は44px以上（見た目を保つなら `::after` で広げる）。
- 押した瞬間に「沈んで戻る」（0.45秒）。全部同じ反応。ただし宿題チェックの中だけは付けない（1〜5を連打する所）。
- 動きは transform と opacity だけ。**画面の移り変わりはフェードだけ**（上下左右に動くのは気持ち悪い。本人）。紙（ポップアップ）は拡大しながら出て縮みながら消える。短すぎる動きはせっかちに見える（apple.com より少し短く）。`prefers-reduced-motion` では全部止める。
- 別ページへ飛ばさない。詳細は**紙**で出す。開いてもページは1pxも動かない。閉じる道は×と暗がりの2つ。
- 保存や操作のあとに「よみこんでいます」へ戻さない。一覧は裏で取り直す。今いるタブをもう一度押したら一番上へ。遅れて届いた結果で別の画面を描かない。

### 7.4 やる気と公平
- 順位を出さない。責める数（未提出・遅れ）を祝いの場所に出さない。0 の札は出さない。
- 生徒には％を出さず、言葉で。前向きなひとことだけを大きく。
- 講師の作業を増やさない（ほめる所を選ぶ入力などを足さない。いまある評価とひとことだけを使う）。
- **紙の子を不真面目に見せない。評価を付ける講師を悪く見せない。使わない講師を目立たせない。**

## 8. 踏んだ罠（すべて実際に起きた。別のサービスでも必ず踏む）

### 8.1 データが消える
| 症状 | 原因 → 対処 |
|---|---|
| ログアウトで直前の学習が消える | 送信待ちを送らずに捨てていた → 出る前に送りきる |
| オフラインで解いた20問が消える | 衝突を「丸ごと・時計が新しい方が勝つ」で解いていた → **項目単位で合流、回数の多い方** |
| 空の状態で本物を上書き | 読み取りが空のときに保存していた → **空なら書かない** |
| 遮断されているのに警告が出ない | `try{}catch{}` で握りつぶし、「遮断」と「まだ空」を区別できなかった → **保存できるかは実測でプローブ** |
| 教材を1語挿したら全員の進捗がずれた | 配列の位置を ID にしていた → 中身由来の ID |

### 8.2 権限・漏れ
| 症状 | 原因 → 対処 |
|---|---|
| 誰でも講師画面に入れた | 講師コードが配信される JS に平文 → 講師はサーバ経由だけ |
| 担当外の学年の進度を書き換えられた | 範囲を絞らず1文書を丸ごと保存 → 担当の行だけ差し替え |
| 公開したら全員が締め出された | 中継の後ろで全員が 127.0.0.1 に見え、試行制限を共有 → 中継のヘッダを信じる（相手が自分のときだけ） |
| 同じ画面で講師⇄生徒を切り替えると前の人のお知らせが残る | 控えを持ち越した → サインインとサインアウトで全モジュールの控えを消す |
| 教材が未ログインで丸取りできる（**いまも残る最大の穴**） | 教材を静的ファイルで配っている → 教材に依存しない設計（§10） |

### 8.3 画面が嘘をつく・壊れる
| 症状 | 原因 → 対処 |
|---|---|
| **検査が全部通っていたのに「次の授業 総復習（7/14）」（9月に7月の回）** | 出せない過去の回を「次」にしていた → 直し、**意味の検査**を作った（§9.1） |
| 18パック2,847問がアプリから見えていなかった（検査は「指摘0件」） | 登録関数を呼ばず独自の変数に書いていた → **動かして確かめる検査**（ファイルを見る検査では原理的に捕まらない） |
| 教材にキリル文字・ハングル・英単語の断片が35件混入 | 手で書いていた → 教材は生成器で作り、検査を通らないと1行も書き出さない |
| 生徒が写真を送れない | iPhone の写真 3〜5MB を縮めずに送り上限超え、HEIC を受けられず、カメラは1回1枚なのに選んだ瞬間に送っていた → 縮めてから・ためてから送る |
| 写真を縮めたつもりが元のまま | CSP が `blob:` を許しておらず `createObjectURL` の読み込みが必ず失敗 → `createImageBitmap` → data: URL |
| 部品を並列で取るブラウザで白い画面 | 標準の HTTP サーバの待ち行列が5 → 128 |
| 「ためしに見る」が消えた | CSS のクラス名の衝突（`.ghost`） |
| Safari で全ページが縦一本 | Grid の自動配置に頼っていた → 列を明示・container query |
| Safari で印の位置がずれた | SVG の circle に CSS の transform → SVG の属性で回す |
| 1人の講師が進度を保存しただけで学校じゅうの対策テストが消えた | 「使わない」の読み方が画面とサーバでずれた → `enabled:false` だけが「使わない」 |
| ログインしても遷移しない | ID が placeholder の薄い灰色で入力済みに見えた |
| 講師画面が開かない | 担当全員の進捗を丸ごと取得（250名で23MB）→ 1人200バイトの要約、開いたときだけ詳細 |

### 8.4 作り方・検査の罠
- 検査が誤報だらけになると人は検査を見なくなる。
- 裏に回ったタブはタイマーが1秒1回に間引かれる。
- デモだけの直し方をしない（デモは本番と同じ関数を通す）。デモは空の ROOT に作る。
- 一時領域は消える。道具は原本の側（`scripts/check/`）に置く。
- 部品を作る前に、遠くから見た画面の絵を描く（導入の段階の最初の形は「段階を選ぶ部品を行ごとに置いただけ」で、60個の灰色のボタンになった）。

## 9. 検査と自律の考え方

### 9.1 意味で確かめる
「動く」ではなく「**意味が合っている**」を確かめる。画面ごと・操作ごとに三つの問いを立て、答えを `expect.py` に**そのまま条件として書く**（文書だけに書いた不変条件は守られない）。

| 問い | 例（成績のコースの画面） |
|---|---|
| 何のための画面か | 講師が、このコースの生徒がどの単元でつまずいているかを1分で掴み、次の回の宿題を変えるため |
| こうなっていなければおかしい | 次の授業は今日以降。単元は日付の順。人数は受け取る生徒の数。理解度は0〜100。成績のコース＝使っているコース全部。写真は段階2以上だけ。**前回より25%以上減っていない** |
| こうすればもっと良い | 次の授業に曜日を添える（→ 実施済み）。50%以下の生徒の行から答案へ1タッチ |

不変条件の見つけ方：その数字の出どころを関数名まで辿る／境界を置く（使い始めが学期の途中・0人・全部紙・日曜・夏時間）／二つの経路で同じ数を出す（API と画面）／前回との差（ledger）／日付は必ず疑う。
直すときの決まり：**不具合を1つ直したら、それを捕まえる不変条件を1つ足す。数が減っていたら、理由を言えるまで配らない。**

### 9.2 自律の作法
- 指示の範囲内は聞かずに完了まで進める。範囲外・権限の拡張は提案して止まる。
- 作業の最後に「改良の種」を1つ以上書き、効果が大きく手間の小さいものを1つ提案する。
- 文脈の圧縮で大目標・美しさ・わかりやすさが薄れる。だから**判断の軸を1枚（北極星）に固定し、圧縮のあと・着手前に必ず読み直す。**
- 複数のセッションが同じ原本を触る。着手前に他のセッションの更新（ファイルの更新時刻・計画の完了印）を確かめ、変わっていたら写さずに聞く。

## 12. 別のサービスを作るときの初期値

**持っていくもの（ほぼそのまま使える）**
1. 大目標を1枚に固定する（北極星）。買い手が誰かを最初に決め、その買い手の「欲しい」だけを作る。組織に売るなら証拠を先に。
2. 部分導入を前提にする：使う人・使う単位・使う深さを、利用者自身がワンタッチで選べる段階にする。**使わない人には何も見えない・何も求めない。**
3. 併走の原則：新しい道具が観測できないものを「やっていない」と言わない。観測の割合を数字に添える。
4. 個人情報を持たない設計（ID だけ、対応表は手元）。テナントの分離はパスの1か所と、合言葉から引く校舎で。
5. 判定はサーバ。発行のときに確定。派生値は保存しない。ID は中身から。時計に頼らない。空なら書かない。保存は実測で確かめる。
6. 依存ゼロ・DB 無しで始め、実測で足りなくなってから足す。
7. UI：次にやる1つ／日本語の短い見出し／動作だけを言う／線を引かず面と影で立たせる／色は2色と無彩色／押せるものは必ず押せる／44px／フェードだけ／紙で出してページを移さない／数字は根拠つき、実数で／並びは固定。
8. 検査：壊れていないか（構文・単体・攻撃）に加えて、**意味が合っているか**（画面の目的から決めた不変条件＋前回との差）。不具合1つに不変条件1つ。
9. AI の自律：範囲内は完了まで、範囲外は提案して止まる。権限の線は表にして本人の裁定を受ける。本番は読むだけ、反映は本人。巡回は機械的な部分を1本の要約にまとめ、残りを考えることに使う。

**持っていかないもの**
- 早稲アカ固有の制度（5週周期・クラスの記号・シラバス・教材の名前）。新しいサービスの周期をまず調べ、それを全体の単位にする。
- 前身から残った古い書きつけ（`CLAUDE.md` の「デザイン」節の黒地・Fraunces・明朝、`デザイン仕様書.md` §3 の「英語1語＋日本語」の見出し）は**いまの形ではない**。いまは明るい地・ゴシック・日本語だけの見出し。
- 「時短」「仕組み化」「手間はへる」という売り文句。

**最初の1週間でやること**
1. 本人に確かめる：買い手は誰か／利用者は誰で、何が苦手か／組織との関係と権限の線／個人情報と教材の扱い／予算。
2. 北極星を1枚書き、本人に読んでもらう。
3. 画面を作る前に、遠くから見た1枚の絵（次にやる1つは何か）を描く。
4. 最初の不変条件を3つ書き、検査を先に作る。

## 追記（2026-09-30）―― お金をいただいて運用するための土台（本導入は 10/15、遅くとも 10/31）

前提が変わった：**これからお金をいただいて実際に運用する。妥協は要らない。** それに合わせて、口座まわりを作り直した（決めごとは `CLAUDE.md`「席・管理者・管理ページ」、安全の説明は `SECURITY.md` 8章、手順は `Claude outputs/手順-席と管理ページ（本導入）.md`）。

- **席（seat）。** クラスごとに先に30席（ID と合言葉）を作っておく。渡していない席は、名簿にも宿題にも成績にも出ない。カードを持った本人がはじめて入ったとき（か、管理ページで「使う」、か、オンラインで引き換えたとき）に、在籍の生徒になる。
- **サーバは、合言葉そのものを受け取らない。** 作るのは管理者のブラウザか手元の道具。入るときは、端末が「証明」だけを送る（SCRAM の考え方）。サーバが持つのは、証明を確かめるための値だけで、それだけでは入れない。
- **渡し方は2つ。** 紙のカード（QR を読むと、そのまま入れる）と、オンラインの生徒への「1回だけ使えるリンク」（開くと、本人の端末が本物の合言葉を作る）。
- **管理ページ（/admin）。** 席と合言葉／講師と担当／生徒に出ているもの／カード／報告。クラス替え・クラスを足す・管理者を足す、もここで。1つの操作が1つの小さな保存。管理者は、答案も記録も読めない。
- **報告が集まる。** 生徒と講師の右上メニュー「うまく動かないとき」と、画面が自分で拾ったエラーが、管理ページの「報告」に集まる。
- **隙間を鍵で塞ぐ。** 鍵を1つにし（スレッドにもプロセスにも効く）、「確かめる」と「使う」を同じ鍵の中に置く。検査は、直した所をわざと壊して × になることまで確かめる。
- **本物の校舎とデモを分ける。** 本物は `waseaca-london`、`london` は架空のデモ。本物の校舎があるとき、ふつうの入口に「ためしに見る」は出ない（デモは `/demo`）。デモの作り直しは、サーバを止めない。
- **使っていないものを見せない。** 毎日テストを使っている教科が無い生徒には、毎日テストのタブも札も出さない。

別のサービスへ持っていけること（§12 への追加）：
1. 利用者の口座は「先に作っておき、使い始めたときに生きる」形にすると、配る人にも使う人にも追加の操作が要らない。ただし**使っていない口座を、数える所に混ぜない**（印ではなく、種類で分ける）。
2. 秘密は、サーバに届かない所で作る。サーバが持つのは、確かめるための値だけ。入るときも、秘密そのものは送らない。
3. 離れた相手には、秘密を送らずに「1回だけ使える引き換え」を送る。秘密は、相手の端末で生まれる。横取りは、本人が引き換えられないことで分かる。
4. 鍵は1つ。確かめてから書くまでを、同じ鍵の中に置く。コマンドもサーバも同じ鍵を持つ。
5. 強さは、試行制限ではなく秘密そのものに持たせる。入力のゆれ（大文字・全角・区切り）は、くらべる前にそろえる。
6. 自分で作った部品（QR・入る手順の計算）は、作った側とは別のもの（OS の読み取り・別の言語の実装）で読み直して確かめる。
