# 検査の思考法 ―― 「動く」ではなく「意味が合っている」を確かめる（2026-09-23）

きっかけ：成績の画面で「次の授業 総復習（7/14）」が出た。9月に7月の回が「次」になっていた。
検査は全部通っていた（サーバ14本・教材・自己攻撃）。**通っていたのに、画面は嘘をついていた。**
これまでの検査は「壊れていないか」を見ていて、「その画面は何のためにあり、何が出ていたらおかしいか」を見ていなかった。

## 1. 三つの問いを、画面ごと・操作ごとに必ず立てる

| 問い | 例（成績のコースの画面） |
|---|---|
| **何のための画面か** | 講師が「このコースの生徒が、どの単元でつまずいているか」を1分で掴み、次の回の宿題を変えるため |
| **こうなっていなければおかしい（不変条件）** | 次の授業の日付は今日以降。単元は日付の順。人数は受け取る生徒の数と同じ。理解度は0〜100。個別の宿題の人数は生徒数以下。前回の検査より数が2割以上減っていない |
| **ここをこうすれば、もっと良い（改良の種）** | 「次の授業」に曜日を添える。50%以下の生徒の行から、その子の答案へ1タッチで飛べる |

問いの答えは `scripts/check/expect.py` に**そのまま条件として書く**。文書だけに書いた不変条件は守られない。

## 2. 不変条件の見つけ方（機械的でなく、意味から）

1. その数字は**どこから来て、誰が数えたか**を辿る（サーバの関数名まで）。画面が数えていたら疑う。
2. **境界**を置いてみる：学期の途中で使い始めた／期間が終わった／生徒が0人／写真が0枚／全部が紙／今日が日曜／夏時間の切り替え。
3. **二つの経路で同じ数を出す**：API の数と画面の数、講師の画面の人数と生徒の名簿の人数、今日やることの件数と宿題チェックの件数。ずれたらどちらかが嘘。
4. **前回との差**を見る（減っていないか）。ledger.json に前回の数を残し、2割以上減ったら止まる。「なぜこんなに減っている」は人より先に機械が言う。
5. **日付**は必ず疑う。「次」「今日」「今週」「期限」は、今日を動かして（デモの作り直し・本番の翌週）意味が変わる。

## 3. 直すときの決まり

- 不具合を1つ直したら、**その不具合を捕まえる不変条件を1つ足す**（expect.py か test_*.py）。足さずに直さない。
- 「デモだけ」の直し方をしない（publish_courses_past の注のとおり）。デモは本番と同じ関数を通す。
- 画面の出し分けは判定ではない。判定はサーバに置き、画面は従う（導入の段階と同じ）。
- 直した日付・理由・発覚した画面をコードの注に残す（`next_lesson_of` のように）。

## 4. 作業の順番（毎回）

1. 着手前：`expect.py` を走らせ、**今の数を控える**（ledger）。
2. 直す。
3. `server/test_*.py`・`app/tools/check-source.py`・`js構文.sh`・`attack.py`。
4. `expect.py`（意味）。減った数があれば、理由を説明できるまで写さない。
5. `scripts/check/shots.py` で画面を撮り、**自分の目で**「目的に合っているか」を見る。
6. 写す。最後に「改良の種」に1つ以上書く（§5）。

## 5. 自己改良の帳面（指示が無くても進める）

`Claude outputs/改良の種.md` に、検査や実装の途中で気づいた「こうすればもっと良い」を溜める。
書き方は 1行＝1件：`- [ ] （画面）（何を）（なぜ）（効果の大きさ 大/中/小）（手間 大/中/小）`。
作業の最後に、効果が大きく手間が小さいものから**1つ提案する**（作るのは了解を得てから。ただし
不具合・不変条件の追加・文書の食い違いは、了解なしで直してよい）。

判断の物差し（迷ったら上から）：
1. 生徒・保護者・講師の**誤解**を生むもの（嘘の数字・古い日付）＞ 見た目 ＞ 速さ
2. 使わない講師に何も要求しない（部分導入の前提）
3. 概念を増やさない（単純な論理）。増やすなら、同じ概念で置き換えられないか先に考える
4. 本番で起きる条件（学期の途中・混在・生徒0人）で試してから、デモで見せる
